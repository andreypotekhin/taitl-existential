# Structured diagnostics complete-workflow comparison

The latest final-source comparison and interleaved investigation are [recorded here](20261027T074532Z.Diagnostics.md).

## Context and method

Baseline: the complete dirty Sprint 09 working tree at implementation entry, including earlier access/description
changes and untracked sources; HEAD alone was not used. The temporary snapshot is
`/private/tmp/sprint09-diagnostics-baseline-eyw16y5y`. Its 710-file original SHA-256 manifest remains there;
all original file hashes were checked unchanged after the three baseline samples. The identical DiagnosticsBenchmark
harness was added to both trees. The [source manifest](20261027T073911Z.Diagnostics.sources.json) records measured
production/fixture/benchmark/build
sources and the original snapshot manifest hash. Final measured sources were checked against the source capture taken
before the three final candidate runs.

Runtime: OpenJDK Corretto 17.0.15+6 LTS, 64-bit Server VM, Darwin 24.6.0 arm64, 10 logical CPUs. CPU model and physical
memory were unavailable from the restricted system metadata call and remain unknown. Maven compiles for Java 11.
Forked test JVM options: `--enable-preview`; the benchmarks profile excludes the JaCoCo agent. No heap agent was used.

Each variant ran three independent Maven/test JVM processes. Each scenario used three complete warmup workflows and
five measured workflows. Scenario order and harness were identical. Commands, run from each tree separately:

    mvn -q -Pbenchmarks -Dtest=DiagnosticsBenchmark -Dbenchmark.sample=1 \
        -Dbenchmark.warmup.iterations=3 -Dbenchmark.measure.iterations=5 test

Repeat with sample=2 and sample=3. The six linked logs retain every setup/workflow sample, counts, and allocation
values. Setup is measured separately and includes application fixture creation, configuration, and a preparation
handle; library close is outside workflow timing. Each workflow includes begin, reporting, commit, explicit rollback
on failure, and disposal, plus deterministic event-state/count assertions. Recovery includes one rejected handle and
a fresh successful handle. MB means decimal 1,000,000 bytes of current-thread allocation, not retained memory.

Success uses 10,000/50,000 distinct Night City cats, 1/100 matching read checks, and 1/8 repeated reports. Repeated
reports fold to exactly the entity count per handle. Rejection fails only the final entity with one check. Collection
has 1,000 entities and three always-failing checks (3,000 violations). Ordered effects runs one successful effect and
one failed check, skipping every later check/effect/entity. Every mode asserts exact callbacks, violations, folding,
and empty event state after disposal. Retained diagnostics/resource ownership has separate specification acceptance;
these counters do not claim arbitrary leak detection.

Failure modes compare complete evaluation without requesting messages and complete evaluation with default-message
rendering. First/repeated getMessage costs are also timed separately inside render=true workflows and returned lengths
are consumed. Baseline messages are concise; candidate messages include every structured child. These are whole-workflow
averages, not isolated commit latency or latency percentiles. Results use median (range) across three JVM sample means;
JIT/GC, fixed order, short warmup, machine activity, and startup effects limit statistical interpretation. No numerical
gate is established.

## Interpretation and evidence

Success-path median time changes range from -10.0% to +1.9%. No material repeated success-path regression appears in
these samples. The indexed handler traversal avoids the old per-selection iterator allocation; warm 50,000-entity
allocation falls by about 2.4 MB per workflow.

The 3,000-violation rendered workflow rises from 7.7 to 43.1 ms and 12.8 to 44.9 MB. This is the deliberate cost of
detached snapshots, preserved exception details, and a full diagnostic per child; the baseline aggregate message
contained only a short count. First rendering dominates repeated memoized reads. Failure-only allocation and timings are
reported separately and are not used to infer successful throughput.

All 168 scenario samples passed exact callback/violation/folding/disposal checks. No skipped benchmark test or
unavailable allocation measurement was accepted. Independent specification acceptance additionally checks released local
captures, invalidated index views, serialization, concurrency isolation, and no entity rendering.
