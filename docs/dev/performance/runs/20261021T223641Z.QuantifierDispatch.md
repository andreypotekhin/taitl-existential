Processor model, physical core count, and memory: unavailable in the sandbox. One test JVM and one workload thread per
sample, with `--enable-preview`; the benchmark profile overrides the ordinary JaCoCo agent argument.

The unchanged CustomTransactionBenchmark runs static context, configured transaction, and caller-supplied transaction
scenarios in that order. Each operation begins a transaction, reports one Cat update, and commits, with one update
effect incrementing a counter. Warmup: 5,000 operations per scenario; measurement: 50,000. Configuration/setup and
close are outside the timed region. There are no fluent expressions, so this measures dispatch overhead rather than
the cost of previously skipped rules. Per-rule evaluation correctness is established by the acceptance tests.

The samples overlap and vary substantially within each phase, with opposing median changes across scenarios.
They do not establish a consistent performance regression or improvement. Fixed scenario order, JIT/GC, machine load,
and the small sample count limit inference; these are averages rather than percentiles or confidence intervals.

For E split event keys and T distinct expanded TypeKeys, the repair performs O(E) existing-key collection plus O(T)
expression-key creation per lookup. It adds T metadata keys to the EventField cache key; it does not add entity values
or an entity-dependent cache dimension. On a cold lookup, existing configured-expression references join the cached
ordered list; warm lookup reuses it. An active expression adds its own evaluation work, which cannot be compared to
the formerly skipped implementation as an equivalent workload. Allocation/retention and larger rule/type cardinalities
are not measured by this harness.
