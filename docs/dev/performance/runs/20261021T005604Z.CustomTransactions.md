## Environment and workload

JDK: Amazon Corretto 17.0.15+6-LTS (64-bit Server VM); Maven 3.9.10.
OS: macOS 15.6.1; architecture: arm64; processor: Apple M4, 10 physical/logical cores.
Surefire JVM option: `--enable-preview`; no task-supplied JVM tuning. Background/thermal state was not controlled.
Each of three independent Maven invocations starts a fresh benchmark test JVM. Within each JVM scenarios run in fixed
order: static-context, configured-transaction, custom-transaction. Each scenario has 5,000 warmup transactions and
50,000 timed transactions. One thread updates one Cat per transaction; an update effect increments an AtomicInteger.

The timed region includes begin, one update, and commit. Factory-created and caller-supplied transaction construction
is included in their respective paths. Scenario initialization/configuration, warmup, and library close are excluded.
Metrics are mean elapsed microseconds per transaction and derived throughput; allocation/memory were not measured.

## Reproduction

From the repository root, run this command three times as separate invocations:

    mvn -q -Pbenchmarks -Dbenchmark.warmup.iterations=5000 -Dbenchmark.measure.iterations=50000 test

Each invocation exited zero and ran the CustomTransactionBenchmark test. This profile does not run the ordinary suite.

## Interpretation and follow-up

This is the initial recorded session, not evidence of improvement over another revision. Fixed scenario order and
single-JVM scenario sequencing can affect the relative numbers; do not conclude that custom transactions are
intrinsically faster. The spread between samples also prevents a justified automated percentage threshold.
Historical timings in the custom-transaction execution plan lack a matching environment/workload record and are not
a regression baseline. Link this session from future comparable measurements and record changed workload/harness
identity when extending it. See [guide](../Readme.md) and [topic summary](../topics/CustomTransactions.md).
