## Method

From each tree, run sample=1,2,3 in fresh JVMs:

    mvn -q -Pbenchmarks -Dtest=TransactionDiagnosticsBenchmark -Dbenchmark.sample=1 \
        -Dbenchmark.warmup.iterations=3 -Dbenchmark.measure.iterations=5 test

Each row reports average time and current-thread allocated bytes for five complete workflows after three warmups.
One SUCCESS workflow is 1,000 begin/read/commit/dispose transactions. Error workflows attempt 1,000 rejected reads
or missing-ID lookups, explicitly dispose the handle when present, then complete one fresh successful transaction.
ROLLBACK_ONLY first reports a failing read/commit and explicitly rolls back once; CLOSED closes before rejection.
Setup/configuration/initial begin-close is separate; final library close is outside timing. Rendering=false never
requests the guard exception message. Rendering=true requests it twice, including first rendering and memoized reuse;
it does not isolate those two calls. Baseline messages are plain. Prior failing evaluation rendering is excluded.

Every workflow asserts exact callbacks/checks, exact stock exception classes, released event state, and registry size
zero. SUCCESS has 1,000 checks/no rejection; CLOSED and MISSING each have one check/1,000 rejections; ROLLBACK_ONLY has
two checks/one explicit rollback/1,000 rejections. There are 21 measured scenario samples per final variant, 42 total,
each averaging five independently checked workflows. All counters and cleanup assertions passed. Allocation data is
positive and available; decimal MB means bytes/1,000,000. It measures created bytes, not retained heap or ownership.

The first three baseline/candidate pairs were interleaved. After inspecting their failure cost, the factory was
simplified to construct one exception after snapshot creation instead of constructing two and copying stack frames.
The final candidate then ran in three fresh JVMs. Thus final baseline/candidate timing is not fully interleaved.
No Maven builds ran concurrently with measurements. Scenario order is fixed, and JIT, GC, startup and background
activity can influence short samples. Medians/ranges are descriptive, not confidence intervals or latency percentiles.
No numerical gate or success speedup is inferred.

Success ranges overlap and allocation varies with JIT; source inspection confirms that successful guard/lookup
branches do not acquire the factory or create diagnostic data. Do not infer a success-path regression or improvement.
Unrendered rejection costs rise by about 0.56–0.75 MB per 1,000 attempts (roughly 560–750 bytes per rejected request),
for snapshot/list/string construction. First detailed rendering plus repeated access adds a further 2.18–3.53 MB per
1,000 attempts relative to unrendered candidate workflows. The additional failure-path time and allocation buy stable
codes, detached facts, remedies and escaped multiline output; they are explicit costs, not throughput improvements.

## Investigation: redundant exception construction

The initial candidate produced the following measurements. They are exploratory evidence for the implementation
change, not the final source in the manifest. Its factory created a fallback Throwable, then a decorated Throwable,
then materialized/copied the fallback stack. The final factory builds detached data first and creates one stock
exception, using the plain constructor on snapshot failure. No original callback Throwable exists at these guards.

| Scenario / rendering | ms/workflow median [range] | decimal MB/workflow median [range] |
| --- | ---: | ---: |
| SUCCESS / false | 15.4479 [14.8523, 16.3762] | 25.5100 [25.3636, 25.5211] |
| CLOSED / false | 14.3504 [14.2420, 14.6360] | 11.3592 [11.3591, 11.3595] |
| CLOSED / true | 15.4383 [15.2274, 15.4618] | 14.6341 [14.6259, 14.6388] |
| ROLLBACK_ONLY / false | 13.2359 [12.9258, 13.4527] | 11.6056 [11.6055, 11.6056] |
| ROLLBACK_ONLY / true | 13.5377 [13.0453, 13.6746] | 15.0917 [15.0803, 15.0946] |
| MISSING / false | 13.1028 [12.4525, 13.2938] | 11.0199 [11.0193, 11.0251] |
| MISSING / true | 12.4833 [12.3829, 12.5827] | 13.1839 [13.1755, 13.1978] |

Removing the duplicate construction reduces unrendered failure allocation by about 7.53 MB per 1,000 rejected
requests in these samples and substantially lowers their observed elapsed time. Richer-message costs remain above
the plain baseline. Correctness tests separately verify fallback, Error propagation, catch types and cleanup.
