## Environment and workload

Amazon Corretto 17.0.15; Maven 3.9.10; macOS 15.6.1 arm64; 10 reported online logical processors.
Exact processor model/physical core count and memory were not collected. One workload thread per fresh test JVM,
with `--enable-preview`; the benchmark profile overrides ordinary JaCoCo instrumentation.

RelationshipBenchmark uses list, LinkedHashSet, LinkedHashMap membership, and a key/value relationship predicate at
16, 256, and 4,096 entries, in that cardinality/source order. Each operation begins a transaction, reports explicit
Cat before/after values, and commits. Two rules validate All-Exists and color-preserving evolution. The reported
after-value is an equal snapshot of the last inserted source entry, so scan-based paths recover the last match.
A final map/256 scenario reports the same transition 16 times per transaction; validation folds it to one event.
Setup/configuration, source creation, and close are outside timing. Warmup: 2,000 transactions per scenario;
measurement: 10,000. Configuration is reused, each transaction is fresh, and source contents remain fixed.

Both phases include the Night City equality correction and runtime-index clearing on transaction completion.
The performance-relevant before/after difference is membership-only Exists: the baseline recovers a stored source
object after indexed membership; the after phase delegates directly to contains/containsKey. Predicate-bearing
relationship checks retain their original-object scan. Error-only diagnostic wording does not enter the timed path.

## Interpretation and limits

At 4,096 entries, median set membership changed from 23.5 to 6.4 microseconds/transaction and map membership from
28.6 to 5.3 microseconds. The map after range is 5.2–6.5 microseconds versus 24.1–29.7 before; the set after range is
5.8–7.0 versus 22.8–27.6 before. Four deterministic tests prohibit iteration in membership-only map/set checks,
independently establishing elimination of the scan. Positive and negative membership cases and source-key/value
identity tests confirm the predicate-bearing forms retain their semantics.

A list's membership remains O(N); a standard hash set/map now uses its expected O(1) membership operation. Actual
complexity depends on the source implementation and key contracts. Recovering the original stored key/value for a
predicate remains O(N) with these general source interfaces, which do not expose a direct stored-key lookup. The
4,096-entry relationship scenario retains roughly 26–36 microseconds in the after samples; no indexed-relationship
speed guarantee is claimed. Maintained indexes remain a separate capability.

The first scenario shows substantial JIT/startup variation and fixed scenario order affects comparisons across source
sizes. These three-sample medians/ranges are descriptive, not confidence intervals or latency percentiles. Timings
exclude source maintenance and do not measure allocation, retained heap, contention, or arbitrary cardinalities.
The repeated-report scenario still pays event/report/indexing costs despite folded validation; it is not evidence
that duplicate reports are free. No automatic regression threshold or application latency budget is asserted.

Resource evidence is separate: relationship acceptance retains the closed transaction handle and verifies its event,
event-key, and type-key indexes are empty after successful completion or explicit rollback. Failed commit vacates ID
lookup; source maps remain unchanged. These checks do not establish global cache bounds or library-close behavior.
