# Diagnose rejected transaction access

This living ExecPlan follows [Plans.md](../../auto/Plans.md). Status: complete; archived after verification.

## Purpose / Big Picture

An application can distinguish a completed handle, a rollback-only handle, and an unknown transaction ID through
DiagnosticCode rather than message parsing. Existing catch types and lifecycle behavior stay available. For example,
a read attempted after a failed checkpoint reports TRANSACTION-ROLLBACK-ONLY with the operation and a specific cleanup
remedy; ID lookup of that detached handle reports TRANSACTION-NOT-FOUND without inventing its former operation.

The authoritative contract is [transaction state diagnostics][spec]; the [design][design] explains ownership and cost.
This is the next bounded slice of approved S02222601 and T10272601, not all-public-exception completion.

## Surprises & Discoveries

ConcreteTr.requireOpen already distinguishes closed from rollback-only and allows explicit rollback on rollback-only
handles. These guard failures happen before checkpoint/commit enters its failure-state transition. TrRegistry.get
cannot know the former operation after detachment; it must not retain a failed handle to improve a diagnostic.

Closed memo lookup uses a separate IllegalStateException guard in requireMemos. It is outside this selected contract;
changing its exception hierarchy would exceed the stock-type-preserving scope. Memo registration uses requireOpen
and is covered. A live index view routes through requireOpen, but acceptance revealed that a disposed view clears
that guard and has a separate rejection path. Include that path using its already retained operation string and no
transaction ID; never retain an owner merely for diagnostics.

Initial measurements exposed redundant failure allocation: creating a plain fallback exception, then a decorated
exception and copying the stack. State guards have no prior business Throwable to preserve. Build detached data first,
then create one stock exception, using the original plain constructor if snapshot construction fails. Re-run candidate
measurements and retain the initial samples as an investigation.

## Decision Log

On 2026-10-27, select TRANSACTION_CLOSED, TRANSACTION_ROLLBACK_ONLY and TRANSACTION_NOT_FOUND, displayed with hyphens.
Keep direct guard failures as exact ExistentialException and registry misses as exact NotFoundException. Add only a
three-argument message/cause/Diagnostic constructor to NotFoundException. Existing constructors stay plain.

Snapshots contain known operation, requested action and transaction ID as strings. Disposed managed views use the
same closed code but omit their unknown transaction ID; ManagedAccess.check owns that separate failure branch.
Guard stage/event/type/rule/context and children are absent. Requested commit/checkpoint/rollback map to those
boundaries; reporting/memo registration maps to report; index/memo queries have unknown boundary. Registry misses have
unknown operation/boundary. Unknown facts are omitted. evaluationStopped is false because these guards did not start rule evaluation. No cause of the
original rollback-only transition is inferred or retained. Closed takes precedence over rollback-only after disposal.

Use separate TransactionDiagnosticLogic and BuildTransactionDiagnostic delegates so existing rule construction remains
focused. Invoke Creator.singleton only inside the existing rejection branches, preserving successful-path structure.
Retain original fallback messages, construct one stock exception with or without a snapshot, catch RuntimeException
for decoration fallback, and allow Error to propagate. No callbacks, entity rendering, stack scanning, ambient state,
or new registry is added.

## Validation and Acceptance

A completed handle yields TRANSACTION-CLOSED; a detached but open failed handle yields TRANSACTION-ROLLBACK-ONLY;
its ID or an unknown ID yields TRANSACTION-NOT-FOUND. Catch types, closure, explicit rollback callbacks and fresh retry
stay unchanged. Raw fields remain unchanged while control characters are escaped in messages. No entity toString or
rule invocation occurs for rejected access. Retained diagnostics remain immutable, serializable and usable after
handle/library close, and contain no entity, index, callback, Throwable or live owner. Construction/rendering failure
keeps the original fallback failure; repeated messages are memoized under the existing contract.
