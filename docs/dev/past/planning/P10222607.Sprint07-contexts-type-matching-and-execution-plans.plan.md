# Deliver ordered type matching and compiled runtime execution plans

This delivery execution plan is a living document maintained under `docs/dev/auto/Plans.md`. Keep Progress,
Surprises & Discoveries, Decision Log, and Outcomes & Retrospective current. A runtime `ExecutionPlan` is a library
concept, not this Markdown delivery plan. Written on 2026-10-22; reopened on 2026-10-23 after identifying unfinished
matching optimization. Completed on 2026-10-23 after production selection integration and final comparative evidence.
The archived record preserves implementation steps, discoveries, and the reason for reopening.

## Purpose / Big Picture


Applications should report tens of thousands of entities without repeatedly discovering which rules apply. Users
configure parent/wildcard contexts and rules for entity classes, interfaces, and generic types; the library derives an
ordered runtime execution plan. Validation-only operations cheaply record reports and perform their checks at
checkpoint/commit. Existing immediate rules, input errors, callback order, rollback, and shutdown keep their timing.

The primary workload is 10,000–100,000 reported entities, 20–200 distinct class/generic descriptors, and 100–500
rules.
Night City supplies realistic reusable data/model/configuration fixtures rather than benchmark-only dummy domains.
Success is demonstrated by direct user-story specifications, instrumentation proving work is shared per dispatch
signature, comparable performance/resource records, and the root, independent consumer, and reactor builds.

## Context and Orientation


The completed continuation compiles RuleInventory declaration IDs and raw-type buckets, checks structural patterns,
and resolves immutable RuleSelections through compact DispatchSignatures before expansion. EventField owns bounded
prepared generations; transaction overlays keep local closures isolated. ConfigurationLogic and OperationIndexes own
bounded operation profiles/inventories. TypeHierarchyLogic holds ClassValue metadata, and TypeMatchingLogic owns
bounded warning suppression. Tests and the final performance record below cover their observable behavior/resources.

The following entry-baseline notes explain the constraints that guided implementation. References to eager storage,
expanded-key lookup, or unconditional stage activity describe that starting point and are superseded by the completed
implementation described above and the topic design.

The root Maven project builds `com.taitl:existential:0.0.1`. `examples/night_city/pom.xml` independently consumes the
installed library. `reactor/pom.xml` combines the builds. Root tests also compile Night City sources as shared fixtures;
those classes must remain excluded from normal and assembled library artifacts. Compiler release 11 does not establish
runtime support beyond the actual recorded environments.

`src/main/java/com/taitl/ex/logic/configuration/ConfigurationLogic.java` orchestrates configuration and per-operation
indexes. `configuration/indexes/actions/IndexConfig.java` currently scans declared contexts using
`configuration/rules/MatchParentName.java`. `MaintainGlobalOrder` assigns ordinals in indexing encounter order.
`transactions/actions/CreateTran.java` selects context-created transactions; its selection must agree with indexed
context order. Context declaration identity is distinct from context name or callback-object identity.

`src/main/java/com/taitl/existential/keys/TypeKey.java` currently keeps a formatted string and discards captured
reflection Type metadata. `ex/common/helper/lang/Generics.java` reads anonymous-subclass generic information.
`GenericsVariants` and `evaluation/events/split_events/event_splitter/SplitTypeKey.java` expand generic names; nested
expansion is not proof of Java-compatible callback argument types. A type descriptor means a structural description
with actual class identity, parameter arguments/bounds, and known versus unresolved information, not only a string.

`configuration/indexes/data/EventField.java` lazily merges/sorts handlers for a MultiKey and caches them.
`EventFieldOverlay.java` combines shared context and transaction-local selections. Retain and extend these concepts.
`evaluation/events/split_events/SplitEvent.java` currently constructs expanded keys before reaching that cache.
`events/actions/ReceiveEvent.java` constructs a RuntimeKey for report-time processing; `indexing/IndexingLogic.java`
constructs keys again for storage. The runtime event set in `indexing/data/EncounteredUniqueEvents.java` preserves
encounter order and folds by RuntimeKey's event/type/entity identity.

`ex/concrete/ConcreteTr.java` currently activates begin/immediate windows unconditionally in onBegin and eagerly
creates stage/memo containers. These booleans represent lifecycle windows, not proof that a stage has applicable
rules. `transactions/actions/BeginTran.java` calls begin lifecycle behavior before
`stages/validation/actions/PrepareTransaction.java` prepares local overlays. A begin callback may execute application
code; reporting during setup needs a conservative path. Existing memo checks may depend on the current event payload.

The normative ownership is split deliberately. Context order and diagnostics are in
[Library configuration spec](../../specifications/LibraryAndConfiguration.spec.md#deterministic-context-resolution).
Type compatibility is in
[EventsAndConstraints.spec.md](../../specifications/EventsAndConstraints.spec.md#entity-type-matching).
Compiled selection, specialization, and resource requirements are in
[ExecutionPlans.spec.md](../../specifications/ExecutionPlans.spec.md). Their designs explain the rationale. This plan
summarizes those contracts for delivery; it does not become a second authoritative specification.

## Decision Log


Decision: walk parent levels root-to-operation, applying matching wildcards in declaration order before the concrete
context at each level. Register each matching context once at its earliest matching level and preserve rule order
within each context. Rationale: deterministic composition without an arbitrary wildcard-specificity ranking.
Date/author: 2026-10-22, user decisions.

Decision: asterisk matches within one path segment; matched parent rules apply to descendants. One declaration
discovered through multiple paths executes once per applicable event evaluation; separate declarations remain separate.
Rationale: prevent duplicate discovery from changing side effects while preserving intentional registrations.
Date/author: 2026-10-22, user decisions.

Decision: include entity superclasses/interfaces and provable generic inheritance. Preserve declaration order within
resolved contexts regardless of type specificity. Support upper-bounded wildcards and defer lower bounds. Plain
parameter arguments remain invariant; inherited signatures and explicit TypeKeys provide evidence, not guesses based
on entity contents. Rationale: useful polymorphic rules without passing an unsafe generic argument to a callback.
Date/author: 2026-10-22, user decisions.

Decision: use default-on unresolved-generic warnings through global classpath/environment-file configuration and
existing Ex/per-instance programmatic overrides. Keep current scopes, source precedence, and freeze behavior; add no
process-wide programmatic defaults facility. Rationale: diagnostics use the normal options mechanism.
Date/author: 2026-10-22, user decisions. The selected property is typeMatching.warnUnresolvedGenerics and the planned
flag is Flags.TYPE_MATCHING_WARN_UNRESOLVED_GENERICS, using the next available supported flag bit.

Decision: retain EventField and compare sorted integer membership rows, JDK BitSet, and Java RoaringBitmap in the
initial prototype before selecting their representation. Rationale: include an adaptive compressed candidate without
assuming that compression wins or loses for hundreds of compact rule IDs. Warm selections must avoid repeated generic
expansion and sorting. Date/author: 2026-10-22, user discussion and explicit RoaringBitmap candidate refinement;
concrete representation and capacity remain evidence-dependent technical decisions below.

Decision: conceptualize the compiled result as ExecutionPlan, coordinated by ExecutionPlanLogic and CompileExecutionPlan
with focused actions and business rules. Use ContextResolutionLogic, WildcardContextLogic, RuleOrderingLogic,
TypeHierarchyLogic, and TypeMatchingLogic for their separate policies. Reuse the existing ConfigurationLogic rather
than introducing a duplicate. Rationale: small expressive concepts and delegated behavior follow project style.
Date/author: 2026-10-22, user decisions.

Decision: Night City owns reusable large-population fixtures; the primary benchmark uses dozens to hundreds of distinct
descriptors, not just a handful. Rationale: exercise the intended example domain and independently vary entity,
descriptor, rule, and repetition counts. Date/author: 2026-10-22, user decisions.

Design defaults: a whole wildcard segment requires a present path segment, so /* does not match the root. Unsupported
lower-bound rule patterns fail during configuration; nested matching preserves callback argument safety; explicit
generic information does not suppress known runtime subclass rules. Warning suppression follows bounded cached
resolutions and may repeat after eviction. These details make the agreed contracts concrete without claiming they
were independently selected as new user-facing options. Date/author: 2026-10-22, documentation design defaults.

Decision: reopen Sprint 07 rather than defer representation integration and warm dispatch to a later sprint. Start
with JDK BitSet for cold combination and materialize immutable ordered handler arrays for cached execution. Retain
sorted arrays as the simpler comparator and fallback when the real-pipeline evidence is inconclusive; RoaringBitmap
remains test-scoped unless an advantage justifies its dependency costs. Rationale: the initial prototype favored
BitSet, but rebuilt every row and did not measure actual dispatch, allocation, or retained memory. The agreed goal is
shared matching work per distinct signature, not merely a faster isolated union. Date/author: 2026-10-23, user
agreement.

Decision: obtain actual cold/warm selection and byte-level retained-memory evidence before closing the reopened
sprint. Preserve prior build/test results as historical baseline evidence, without promoting them into proof of the
remaining optimization. Rationale: bounded descriptor entries and throughput samples alone do not verify the full
selection pipeline or its resource cost. Date/author: 2026-10-23, agreed continuation.

Decision: use sorted integer membership rows and immutable ordered handler arrays in production. The prepared-row
comparison favors arrays for elapsed time; complete BitSet/array workflow timings overlap, and arrays allocate less.
BitSet's broad-row storage advantage does not justify its enumeration cost or descriptor-duplicated storage model.
Keep BitSet/Roaring only in the comparison harness. Date/author: 2026-10-23, implementation evidence under the agreed
simpler-candidate fallback; exact samples belong to the performance run record.

Decision: bound EventField and overlay selections at 1,024 each, operation inventories/profiles at 128 operations,
and warning suppression at 64 signatures per evaluation instance. Retain the 4,096-entry legacy descriptor bound with
weak class references. FIFO eviction and miss computation outside insertion locks preserve cheap hits and safe
recomputation; measured 200/500-signature cases and explicit churn cross these capacities. Date/author: 2026-10-23.

### Milestone 2: Resolve technical choices with a bounded prototype


Prototype internal structural descriptors retaining captured reflection Type/Class information while preserving
TypeKey construction/factory/string/equality compatibility. Prove metadata reaches the matcher without guessing a
class from an ambiguous simple name. Keep metadata transfer internal through the existing facade/concrete delegation
style; do not publish type registries, strategy APIs, or an execution-mode switch. Record the exact bridge used in this
plan before production integration. String-only keys retain symbolic exact matching; hierarchy matching needs reliable
metadata from the key or runtime signatures.

Compare sorted int arrays, JDK BitSet, and Java RoaringBitmap membership rows with the same descriptors, pattern
buckets, declaration identities, and final ordered selection. Roaring partitions integer IDs into chunks with array,
bitmap, or run representations; measure its own preparation costs along with the operations it accelerates. Include
sparse/broad applicability, upper-bound patterns with one shared raw generic class, and larger sparse/dense/clustered
ID stress cases labelled separately from the primary workload. Keep configured IDs compact in production; stress
layouts do not justify wasting ID space to favor a candidate.

Measure construction, union/intersection, enumeration into the same ordered EventField sequence, cold/warm complete
workflows, allocation, retained heap/entries, and simultaneous first use. Treat optional run optimization as preparation
work and include its cost whenever used. Do not compare serialized byte counts to another candidate's actual heap
footprint. Represent final EventField selections as compact immutable sequences. Use a controlled reference matcher
only in tests/benchmarks to compare results, not a second production engine configured by users.

Select the lowest-complexity representation that is competitive for the primary workload. A consistently measurable
advantage can justify the more complex candidate; inconclusive evidence selects the simpler sorted-array candidate.
Keep Roaring as a test-scoped prototype dependency, pinning and recording a Java-release-compatible version. It must
not appear in public library signatures or consumer/runtime dependencies during the comparison. Adopt it in production
only if the measured benefit justifies dependency/artifact consequences. Select a finite cache capacity and eviction
policy from measured
footprint/churn, document it here, and show that high cardinality and negative matches cannot create an unbounded
second cache or warning registry. Cache hits should not require a global lock. The prototype must also settle how
supported transaction-local rule changes invalidate a binding and how begin-callback reporting stays conservative.
These technical choices gate the production integration, not the agreed public behavior.

### Milestone 3: Context/type contracts and diagnostics


Add internal context delegates under `com.taitl.ex.logic.configuration` and type delegates under a focused
`com.taitl.ex.logic.types` package. Use the resolved context sequence for both configuration indexing and transaction
factory selection; do not fix handler order while leaving lifecycle/overlay order on a different context scan.
Retain MatchParentName's builder-validation responsibility separately from runtime selection. Preserve independent
instances, configuration handoff, retry, and factory ownership.

TypeHierarchyLogic resolves superclass/interface signatures using explicit captured arguments and substitutions along
each edge. TypeMatchingLogic considers only relevant configured raw-type buckets, with invariant concrete arguments,
raw/unbounded matching, and upper-bound compatibility where provable. Inherited interfaces form a graph, so traversal
must handle diamonds and repeated declarations. Apply Java-compatible containment through nested generics: a wildcard
inside an invariant enclosing argument does not make that enclosing argument covariant. Preserve old exact/generic
regressions and explicitly identify any previously unsafe structural expansion being corrected, backed by a negative
callback-type test. Reject unsupported lower-bounded rule patterns with a corrective error before their execution.

Add the default-on warning property to `src/main/resources/existential.properties`, the flag to Flags, and atomic
parsing to ConfigureLibrary. Explain explicit TypeKey remediation and link a troubleshooting section. Test classpath
default, environment-file override, Ex/per-instance overrides, independence, malformed-value atomicity, freeze, and
suppression for an intentionally raw dispatch. Unknown arguments are not a license to substitute their upper bound
as a concrete argument. Suppress repeated diagnostics through bounded selection state rather than an independent
ever-growing registry.

Add direct specifications for reverse declaration of parents/children, overlapping wildcard ties at each parent level,
inherited wildcard matches, duplicate discovery, separately registered callbacks, interface diamonds, generic
inheritance/substitution, upper bounds, nested invariance, full/simple naming, ambiguous symbolic keys, and no match.
Add public JavaDocs where these behaviors are exposed; keep internal JavaDocs selective, without routine tag

### Milestone 4: Compile and bind runtime plans, specializing event reporting


Add ExecutionPlan and small supporting data objects under `com.taitl.ex.logic.execution.data`, ExecutionPlanLogic under
`com.taitl.ex.logic.execution`, actions CompileExecutionPlan/BindExecutionPlan/ResolveRuleSelection under its actions
package, and focused RequiresReportTimeEvaluation/RequiresMemo/RequiresStageTraversal rules under its rules package.
The compiler consumes an ordered inventory and produces immutable stage/selection metadata; it never executes a user
predicate/effect. Publish base plans atomically with finalized configuration and cache misses only after success.

Bind the effective plan after transaction factories/supplied instances and required preparation hooks. Preserve begin
lifecycle position and conservative reporting while that setup is incomplete. Keep local closures, prepared indexes,
and invalidation state transaction-owned. Execution activity is the combination of compiled required work and the
existing lifecycle window, not a replacement for lifecycle state.

Extend EventField's lazy selection path to accept an internal compact signature before allocating the expanded
MultiKey.
Include operation/stage, resolved descriptor/runtime class, event-selection shape, and relevant source generation.
Preserve existing entry points through internal adaptation. Cache complete ordered and empty results, retaining
EventFieldOverlay's local ownership. Sharing selection must not share event payloads, before-state memo values, or
per-entity prerequisites; exercise Create/Update/Delete/Transit/Port and compound events on cold and warm selections.

For an effective validation-only plan, bypass begin/immediate selection, intent lookup, event splitting, empty reports,
