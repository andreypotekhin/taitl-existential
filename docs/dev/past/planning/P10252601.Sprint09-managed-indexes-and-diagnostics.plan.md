## Purpose / Big Picture


An application should declare useful indexes and joins, load its operation's working data, and report changes without
writing its own maintenance handlers. Each Tr receives its own index contents. Rules and explicit earlier queries see
up-to-date relationships; work that is definitely boundary-only benefits from event folding. Applications can disable
automatic maintenance for their own efficient implementation. Shutdown diagnostics identify resources the library
actually knows about instead of promising to detect arbitrary memory leaks.

The user authorized implementation on 2026-10-25. Interface and event-order decisions below finalize the selected
contract before Java delivery. All five milestones are implemented; evidence and explicit scope limits follow.

## Surprises & Discoveries


`Transaction.index(name, getKey)` currently returns a named MultiIndex through ConcreteTransaction/TransactionIndexes.
It has no subject TypeKey or event binding. Existing tests of that method cannot establish automatic maintenance.

ConcreteSingleJoin and ConcreteMultiJoin call rebuildViews after individual changes; bulk add loops through those
changes. Their public JavaDocs call left/right maps read-only, but backing methods return mutable maps. These are
maintenance and integrity problems to verify directly, not reasons to silently alter all standalone compatibility.

EncounteredUniqueEvents uses a LinkedHashSet of RuntimeKey; identity folds repeated event/type/object reports in first
encounter order. It is not a last-write journal. A, B, A cannot be reduced to A, B when replacement at the same key is
observable. Existing event folding must remain unchanged while managed maintenance retains its own necessary summary.

Night City's Being has mutable equals/hashCode fields. Identity-based enrollment and separately remembered keys are
therefore material requirements, not merely future support for unusual model classes.

The quantifier design still described retrying a failed checkpoint. This documentation change corrects that passage
to Sprint 08's rollback-only contract. The universal memory-leak claim likewise exceeded observable library ownership.



The initial multi-valued implementation still extracted keys for every report. The repeated-event prototype showed
that no single-valued displacement history exists in this shape, so deferred identity enrollment now extracts once per
pending identity. Single-valued indexes retain acceptance-time extraction. Large-group delta tests require one physical
addition/removal instead of copying/rebuilding all 10,000 members.

Night City's initially reported before-snapshot remained a validation subject after relocation retired its membership.
An all-events Exists therefore correctly rejected it. The shared story now seeds that loaded snapshot and reports the
replacement, preserving event scope. Public troubleshooting explains the distinction.

Coverage inspection found thin explicit-facade exercise, so coherent manual snapshot/group/join scenarios were added in
both policy modes. Source extraction failures are tested both during immediate single enrollment and deferred multi
checkpoint preparation. No GC assumptions or numerical performance gate were added.

## Decision Log


Decision: automatically maintain explicitly declared transaction-local indexes and joins; defer shared mutable contents.
Rationale: a business operation loads/locks its own dataset and releases it at completion. Shared contents would need
separate visibility/invalidation semantics. Date/Author: 2026-10-25 / user.

Decision: separate maintenance from declared user Effects and reuse compiled execution/type-routing concepts.
Rationale: generated effects must not change Sprint 08 failure policy or make relationship availability depend on rule
declaration order. Date/Author: 2026-10-25 / design direction recorded from discussion.

Decision: automatic maintenance and read enrollment default on, support independent opt-outs at app/global, instance,
context, transaction, and index scopes, and permit seed collections plus explicit manual operations.
Rationale: convenience is the default; callers can avoid unnecessary maintenance and read enrollment costs.
Date/Author: 2026-10-25 / user.

Decision: allow uniform empty-index construction at transaction start. Fold pending maintenance between queries and
exploit existing event folding when the index is definitely not needed before the boundary.
Rationale: construction uniformity need not force eager population or repeated physical updates.
Date/Author: 2026-10-25 / user.

Decision: membership uses object identity; single-valued indexes replace a prior value without later resurrection.
Rationale: mutable equality must not strand entries. Successive snapshots of Order 42 illustrate legitimate replacement;
grouping several entities by location instead belongs in MultiIndex. Date/Author: 2026-10-25 / user and discussion.

Decision: report known outstanding shutdown resources without GC-based tracking or a failed-handle registry.
Rationale: deterministic owner accounting is actionable without retaining abandoned transactions.
Date/Author: 2026-10-25 / user.


Decision: apply the same lazy folded path to unknown and known boundary-only consumers, flushing every explicit access.
Rationale: it preserves early-query correctness without inspecting lambdas, and naturally gives boundary-only consumers
folding and deferred population. Two Night City subject types isolate maintenance; the prior dispatch records retain
the larger type matrix. Read-policy and lifecycle combinations use acceptance tests rather than an extra timing matrix.
Date/Author: 2026-10-25 / implementation evidence.

## Finalized Interfaces and Admission Contract


Use immutable `IndexDefinition<I>` tokens with `single`, `multi`, `singleJoin`, and `multiJoin` factories accepting
names, Class/TypeKey subjects, and extractors. I is the existing SingleIndex, MultiIndex, SingleJoin, or MultiJoin
facade shape. `withPolicy(IndexingPolicy)` returns another immutable definition. Register tokens through context and
transaction `index(definition)` methods and builders. `Tr.index(definition)` returns that handle's bound I; unknown
tokens are rejected rather than silently enrolled. Repeated registration of one token is idempotent; distinct tokens
with the same name in an effective transaction are rejected. Standalone APIs and Transaction.index(name, extractor)
retain their current manual behavior.

An IndexingPolicy has optional automatic/enrollReads fields: `inherit()`, `defaults()`, `automatic(boolean)`, and
`enrollReads(boolean)` produce immutable values. App/instance setters and scoped context/transaction setters use
`indexingPolicy(policy)`. Properties are `indexing.automatic` and `indexing.enrollReads`; defaults are true. Resolve
index overrides over transaction overrides over resolved context overrides over app defaults, field by field. Capture
at handle binding; reject scope mutation after configuration/index binding freezes it. File sources validate atomically.

Use bound index addAll/addAllLeft/addAllRight as seed operations. Explicit mutations are permitted in either policy
mode and are ordered with accepted automatic changes; automatic=false skips event matching and extractor calls for
that index. Read reports enroll when enabled; Write reports maintain like Update. RL and Access use read enrollment;
combined marker/custom events are ignored. Explicit bi-event
endpoints retire before and enroll after; Delete removes. Repeated reads/updates are applicable enrollments and can
replace another object occupying a single key. Both matching join sides participate, once each, even for one subject
type. No duplicate mutation is produced by event-family expansion.

Early begin/immediate authorization and rules see previously accepted reports and explicit seeds, not the current
candidate report. Existing stage order is unchanged. After report-time stages succeed, single-valued keys are
extracted/validated and candidates are accepted into
matched maintenance summaries and event recording. Multi-valued keys defer extraction to access/boundary, with
whole-batch prevalidation before application.
An authorization denial does not enroll the candidate. An extractor/seed/maintenance failure makes the handle
rollback-only and detaches active lookup; partially applied data is not queryable. The caller can rollback or close.
Single-valued physical maintenance uses captured validated keys; multi-valued flush invokes the deferred extractors. A
boundary query sees all accepted
reports. This explicit admission model avoids exposing an unauthorized candidate through indexes.

Expression gains a default `evaluate(entity, Tr)` overload preserving old implementations. Add explicit managed
All/Exists forms that resolve the bound token/source for that call; rules never retain one handle's bound view in
shared configuration. Tr is passed through execution, not stored in a mutable shared evaluator or thread-local.
For example:

    IndexDefinition<SingleIndex<Integer, Order>> orders =
            IndexDefinition.single("orders", Order.class, order -> order.id);
    ex.configure().context("/orders/save").index(orders);
    Tr tr = ex.begin("/orders/save");
    tr.index(orders).addAll(loadedOrders);
    tr.update(changedOrder);
    Order current = tr.index(orders).get(changedOrder.id);
    tr.commit();

The compact summary retains identity enrollment, captured keys, and single-valued displacement, plus only affected
keys still present in either the desired or last materialized state. Repeated reports must not accumulate a raw log.
Physical group updates occur on query/boundary preparation. Prototype tests compare this with eager Map-like updates,
including collision/move/delete sequences and inserted early queries. Query views are structurally read-only; explicit
facade mutation methods remain the supported maintenance route.

### Milestone 4: Cleanup and deterministic diagnostics

successful drain, in-flight work, and detached-failure cases without changing shutdown policy semantics.

## Validation and Acceptance


An operation can load independent working data, seed/report it, and use managed All/Exists relationships without writing
maintenance handlers. Read opt-out and fully manual mode work at every declared configuration scope with inheritance.
Two handles using the same definition never observe each other's data. Equal-but-distinct objects remain independent;
in-place mutation and explicit snapshot replacement move entries correctly. Last replacement wins and removing it does
not restore an old snapshot. Seed and read paths reach equivalent supported working sets under their chosen policies.

Early query insertion must not change final contents. Repeated reports without intervening access perform folded
maintenance, not repeated physical work. Begin/immediate rules and effects retain their exact timing; internal
maintenance does not activate the user-effect stopping policy. Successful checkpoints preserve subsequent use;
failed boundaries reject further work while rollback/close dispose resources. Retained closed views release backing
references and reject access. Shutdown diagnostics report known owners with bounded metadata and no GC assumptions.


## Idempotence and Recovery


Keep standalone compatibility tests and V1 consumer workflows running throughout delivery. Stage the work additively;
prototype code is not a supported public API. Failed configuration remains retryable; do not publish partial compiled
bindings. Repeated disposal is safe. Do not add a registry to retain failed handles or undo caller-owned objects.
Resolve any disagreement between folding and replacement before broadening public APIs. No remote publication or
external service action is part of this plan.
