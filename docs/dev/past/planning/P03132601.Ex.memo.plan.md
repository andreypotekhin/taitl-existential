# Implement transaction memo support for accurate before-state bi-events

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan is maintained according to `/docs/dev/auto/Plans.md`.

## Purpose / Big Picture

The library documentation says `Transit` and `Port` handlers should see `x0` as the entity state at the start of the
transaction and `x1` as the final state. Today, split-event lookup often fabricates `x0` by reusing the same live
entity instance for both sides, which makes bi-state rules blind to in-place mutation. After this change, a caller
will be able to register a transaction-local memo before mutating an object, then emit regular `update(...)` or
`delete(...)` events and have downstream `Transit` and `Port` handlers receive the real before-state snapshot.

A user will observe the change in a spec test that mutates an entity in place: without memo support, an
`OnTransit<Cat>` handler sees the same color on both sides; with memo support, it sees the original color in `t0`
and the updated color in `t1`.

## Surprises & Discoveries

- Observation: the approved suggestion proposes `memo(snapshot, type)` overloads, but that API does not identify the
  live object whose identity should later resolve to the memo.
  Evidence: current runtime matching is identity-based via `RuntimeKey.equals(...)`, and memo lookup must therefore be
  anchored to the mutable live object reference, not only to the snapshot instance.

- Observation: synthetic bi-events are already being fabricated during split handling by reusing the same entity for
  both `t0` and `t1`.
  Evidence: `/src/main/java/com/taitl/ex/logic/evaluation/events/split_events/event_splitter/SplitEventType.java`
  emits `new Transit<>(entity, entity)` and `new Port<>(entity, entity)` for `CU`, `UD`, `CUD`, `Create`, `Update`,
  and `Delete`.

- Observation: runtime indexing currently keeps only the post-mutation entity for bi-events.
  Evidence: `/src/main/java/com/taitl/ex/logic/indexing/IndexingLogic.java` stores `RuntimeKey.valueOf(event, type,
  event.t1, fullNames)` with a TODO comment calling out the ambiguity.

## Decision Log

- Decision: base memo lookup on live-object identity and explicit type key, not on snapshot identity alone.
  Rationale: the runtime already uses identity semantics for event/entity matching, and lookup must find the memo when
  the same mutable object instance is later passed to `update(...)`, `delete(...)`, or split-event evaluation.
  Date/Author: 2026-03-13 / Codex Planner

- Decision: implement the public API as `memo(before, live, ...)`, plus transaction-id facade overloads, instead of
  the suggestion's `memo(before, ...)` shape.
  Rationale: storing a snapshot without also naming the live object is insufficient to build an identity-keyed memo
  map. This change keeps the feature implementable and unambiguous.
  Date/Author: 2026-03-13 / Codex Planner

- Decision: reject `before == live` by identity in memo registration and document that callers must pass a detached
  snapshot such as a clone or copy.
  Rationale: the library cannot prove a deep copy was made, but it can block the most common failure mode where the
  exact same instance is accidentally reused for both states.
  Date/Author: 2026-03-13 / Codex Planner

- Decision: memo data lives only for the lifetime of a single `Tr` and is cleared on `close()`.
  Rationale: memo state is transaction-scoped by design and must not leak across transactions or survive rollback or
  commit disposal.
  Date/Author: 2026-03-13 / Codex Planner

- Decision: when an elementary or combined single-entity event would be expanded into a `BiEvent` family and there
  are matching bi-event rules to evaluate, memo presence becomes mandatory and the runtime must fail fast if the memo
  is missing.
  Rationale: silently fabricating `(live, live)` defeats the meaning of `x0` and yields false-positive behavior for
  `Transit` and `Port` rules. A hard failure keeps the semantics honest and teaches the caller to opt in with
  `memo(...)` only when bi-state evaluation is actually needed.
  Date/Author: 2026-03-13 / Codex Planner

- Decision: reject a second memo registration for the same `(live object identity, type key)` pair.
  Rationale: `x0` means "state at the start of the transaction", so overwriting would silently corrupt the original
  before-state. The first registration remains authoritative and duplicate registration fails clearly.
  Date/Author: 2026-03-13 / Codex Planner

## Context and Orientation

This repository is a Java library that evaluates configured rules against events collected during an existential
transaction. The public `Tr` facade delegates transaction state to `ConcreteTr`; transaction-local memo storage is
implemented by `MemoData`. Users can emit elementary events such as `Create`, `Update`, and `Delete`, or bi-state
events such as `Transit` and `Port`.

The runtime expands events into families of matching events. `SplitEventType` defines the event-family mappings and
`EventSplitter` applies them. `ToMemo` turns applicable split templates into memo-backed payloads, while
`RequireMemoForBiEvents` fails early when a relevant bi-event rule has no memo. Presence metadata is precomputed in
configuration indexes rather than discovered by scanning configured rules on each event.

Event reception starts in `/src/main/java/com/taitl/ex/core/existential/ExistentialEvents.java` and
`/src/main/java/com/taitl/ex/logic/events/EventLogic.java`. Unique encountered events are indexed through
`/src/main/java/com/taitl/ex/logic/indexing/IndexingLogic.java` into `RuntimeKey` values. `RuntimeKey` equality is
identity-based on the entity object, which is why memo storage must also be identity-based.

The static facade is `/src/main/java/com/taitl/existential/Ex.java`, the instance facade is
`/src/main/java/com/taitl/existential/Existential.java`, and transaction lookup by string id flows through
`/src/main/java/com/taitl/ex/logic/transactions/data/TrRegistry.java`.

For this plan, "memo" means a transaction-local snapshot of an entity's before-state, keyed by the mutable live object
reference and its type key. "Before-state" means the state that bi-event handlers should observe as `t0` for the
remainder of that transaction. "Detached snapshot" means a different object instance that will not mutate together with
the live object.

## Plan of Work

Milestone 1 establishes transaction-local memo storage and public API entry points.

The implemented public API is exposed through `Tr`, `Existential`, and `Ex`, backed by `ConcreteTr` and the focused
`MemoData` delegate. It uses identity-based live-object lookup and accepts either `TypeKey<T>` or `Class<T>`:

    tr.memo(before, live, typeKey)
    tr.memo(before, live, MyType.class)
    ex.memo(before, live, typeKey, tranID)
    ex.memo(before, live, MyType.class, tranID)
    Ex.memo(before, live, typeKey, tranID)
    Ex.memo(before, live, MyType.class, tranID)

Registration must validate non-null arguments, reject `before == live`, and either preserve the original memo or fail
fast when the same pair is memoized twice. Choose one explicit rule during implementation and document it in the
`Decision Log` with matching tests.

Memo lookup is threaded into the event and split pipeline through `ToMemo`, called by split evaluation and
`EventSplitter`. `RequireMemoForBiEvents` checks configured handler and transaction-intent requirements before the
split is evaluated. `EventType` centralizes bi-event classification, and configuration indexes retain compact bi-key
presence metadata for efficient lookup.

The implemented behavior replaces synthetic same-instance states with memo-aware construction:

- If a memo exists for the runtime entity and split path needs a `Transit`, create `new Transit<>(before, live)`.
- If a memo exists and split path needs a `Port`, create `new Port<>(before, live)` for update-style flows and
  `new Port<>(null, live)` or `new Port<>(before, null)` for create/delete flows exactly as event semantics require.
- If no memo exists and no matching bi-event rules are going to be evaluated, skip bi-event fabrication for that path.
- If no memo exists and matching bi-event rules are present, fail fast with a dedicated memo-related exception message
  telling the caller to register memo state first.

`SplitEventType` remains focused on family mappings; transaction lookup and payload transformation are delegated.
Configuration metadata is checked before handler resolution, avoiding repeated scans over rule collections.

The identity anchor remains the live entity in `RuntimeKey`; the memo snapshot is used only as a bi-event payload.
`SplitEvent` and `EventSplitter` share the memo-aware path for event and intent evaluation.

`MemoException` messages include a remedy and troubleshooting deep link. The gate is limited to paths where a
configured `Transit` or `Port` handler/intent is applicable; Create without a before-state remains valid.

Regression coverage and documentation are in place, including public update/Transit and delete/Port scenarios, missing
memo failures for handler and intent rules, split-level payload tests, transaction memo validation, and cleanup on
transaction close.

Add targeted unit tests around `Tr` memo registration and cleanup, split-event tests proving memo-aware `Transit` and
`Port` payloads, and end-to-end specification tests showing that a user can memo an object, mutate it in place, emit
`update(...)`, and observe correct `t0/t1` in handlers. Update `/docs/dev/Specification.md` with completed user
stories if new spec cases are added, prefixing completed items with `+` per project rules. If the feature introduces a
new error message for invalid memo usage, add a corresponding remedy entry to `/Troubleshooting.md` and deep-link to it
from the exception text.

## Implementation Record

The implementation is in `ConcreteTr`/`MemoData`, the public transaction facades, and focused event delegates:
`ToMemo` builds payloads, `RequireMemoForBiEvents` gates relevant rule paths, and configuration indexes retain
bi-event presence metadata. The live object remains the runtime identity anchor. Documentation and troubleshooting
describe memo registration and missing-state remedies.

Tests cover registration, duplicate and same-instance rejection, transaction-id facade routing, memo-backed update
Transit, memo-backed delete Port, split payload mapping, and transaction cleanup. Missing-memo handler/intent scenarios
are specified but currently fail when explicitly made discoverable; plan closeout remains pending that correction.

## Validation and Acceptance

Acceptance is met when all of the following are true:

- A caller can register a transaction-local memo using `Tr`, `Existential`, and `Ex` APIs with either `TypeKey<T>` or
  `Class<T>`.
- Registering a memo with the same object instance for both `live` and `before` fails fast with a clear message.
- Memo data is visible only within the target transaction and is cleared after transaction disposal.
- An in-place mutation followed by `update(live)` causes split `Transit` handling to expose `t0` as the detached
  before-state and `t1` as the current live object.
- If `update(live)`, `delete(live)`, or a combined event requires synthetic `Transit` or `Port` evaluation and no
  memo is registered, the runtime throws a memo-focused exception with a remedy instead of fabricating `(live, live)`.
- `create(live)` remains valid without memo because creation has no before-state; a synthetic `Port(null, live)` needs
  no memo.
- If no bi-event rules are applicable for that event path, missing memo does not fail unrelated single-entity rule
  evaluation.
- Determining whether bi-event rules are applicable is implemented through precomputed index metadata, not repeated
  handler-list scans on the runtime hot path.
- A create flow without a before-state still behaves as create, and a delete flow can use a memo to expose
  `Port(before, null)` semantics. Both behaviors are covered by specs.
- Existing single-entity behavior remains unchanged when no memo is registered and no bi-event rules are relevant.
- `mvn -q test` passes.

One concrete acceptance scenario should exist as a spec:

    Repository root: /Users/chaos/Files/Dev/Code/taitl-existential
    Command: mvn -q -Dtest=<new spec class> test

The new spec should:

1. Configure an `OnTransit<Cat>` or `OnPort<Cat>` effect that records both colors.
2. Begin a transaction.
3. Register `memo(clonedCat, liveCat, Cat.class)`.
4. Mutate `liveCat.color` from `"Black"` to `"White"`.
5. Emit `update(liveCat)` or `delete(liveCat)`.
6. Commit or checkpoint as needed.
7. Assert that the recorded values are `"Black"` for `t0` and `"White"` or `null` for `t1`, depending on event kind.

One additional regression scenario should exist:

1. Configure a transaction with an `OnTransit<T>` or `OnPort<T>` rule reachable only through elementary event
   expansion.
2. Begin a transaction and mutate a live entity without calling `memo(...)`.
3. Emit `update(...)` or `delete(...)` as appropriate (Create does not require a before-state).
4. Assert that evaluation fails with the memo-focused exception and that the message tells the caller to use
   `memo(...)`.

## Idempotence and Recovery

The implementation is additive and safe to re-run. Memo storage is transaction-local and cleared by transaction
cleanup, so rerunning tests does not accumulate persistent state.

If implementation work partially lands and tests fail:

- Re-run only the new memo-focused tests first to localize whether the breakage is in API registration, split-event
  construction, or handler execution.
- If duplicate-memo semantics prove awkward, prefer failing fast over silent overwrite and record the final rule in
  `Decision Log`.
- If split-event code becomes too large, extract a focused delegate for memo-backed bi-event construction rather than
  further growing `SplitEventType`.

## Interfaces and Dependencies

No new external dependency is needed. Use JDK collections already present in the codebase, especially
`IdentityHashMap`, because memo lookup must follow the same identity semantics as `RuntimeKey`.

The implementation should end with these interface-level capabilities:

- `Tr` can register and retrieve transaction-local before-state memos keyed by live object identity and type key.
- `Existential` and `Ex` can route memo registration by transaction id.
- `EventSplitter` or a dedicated collaborator can build memo-aware `BiEvent` instances from a `RuntimeKey`.
- The runtime can detect whether candidate `Transit` or `Port` split keys would actually hit configured handlers or
  intents, and can require memo state only in those cases.
- That detection is backed by precomputed configuration metadata, ideally keyed by event family and type or `TypeKey`,
  so memo enforcement does not add rule-scan overhead to every runtime event.
- Existing event lookup, indexing, and handler execution still use the live object as the runtime identity anchor.
