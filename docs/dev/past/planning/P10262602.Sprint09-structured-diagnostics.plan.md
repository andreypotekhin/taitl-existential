## Purpose / Big Picture

An application should be able to understand a rejected operation directly from its exception and inspect the same
information as structured fields. Rust-inspired diagnostics provide a primary message/code, rule and invocation
context, useful notes, and specific corrective actions. They do not require compiler-style source spans. After
delivery, a parent/wildcard rule rejection names both the actual operation and original declaration context, identifies
the rule by its existing description, and remains readable after the transaction closes. Consumers may use prose or
ID-like descriptions without heavier declaration syntax.

The authoritative contract is [structured violation diagnostics][diagnostics-spec] and
[constraint descriptions][descriptions-spec]; rationale and ownership are in the
[paired design][diagnostics-design]. This plan organizes delivery and verification, not a second specification.

## Surprises & Discoveries

At baseline, EvaluateIntent.call caught an ordinary constraint violation and returned false. EvaluateSplitKeys then
reports a generic denial. This discarded the rejected declaration's description/cause and had to change without altering
conjunctive intent semantics or declaration order.

RuleDeclaration.id is a compact inventory-local integer, and OrderlyEv.ordinal supplies ordering. Neither is a public
diagnostic identifier. At baseline RuleDeclaration contained event/type/handler/effect but no declaration context.
Provenance must survive configuration indexing and selection, not be reconstructed from the operation at failure time.

Existing fluent rule methods return the enclosing builder, not an individual rule handle. Overloading a String
description parameter with a metadata-object alternative can make existing calls with null ambiguous. A decorator
around Ev may also break EventHandler/Expression classification unless deliberately supported throughout dispatch.
The user rejected both extra metadata arguments and a trailing ruleId method as heavier declarations. Reusing existing
descriptions removes that API problem; the internal declaration-provenance work is still required.

OnException.constraintViolation has a compatibility fallback that classifies a cause-free EventHandlerException by
searching its message text. Classification must happen from typed failures/original text before decoration and then
use the diagnostic code; the multiline primary message must not become a new classification dependency. Ordinary
violations and unexpected callback failures must keep their distinct collection/stop behavior.

ConcreteTr marks checkpoint/commit failures rollback-only after TransactionLogic detaches the registry entry.
Failure-state notes must be finalized at that outer boundary before the exception reaches the caller. Rendering must
not read a live handle later or pretend that an immediate report rejection always made the handle rollback-only.

Implementation observations: intent lookup needed its existing simple/full-name candidate compatibility even when
selection carried occurrences; full-name acceptance caught the mismatch. Exact Surefire outer-class filters omit
nested acceptance, so focused commands now use the wildcard and verify counts. Legacy intent tests needed structured
code assertions and unconditional handle cleanup to avoid hiding assertion failures behind library shutdown.

Final review found shared early-stop notes rendered twice and rollback continuation incorrectly marked stopped.
The renderer now suppresses shared notes while child raw data stays complete; best-effort rollback paths report
continuation accurately. A direct rollback callback case verifies later callbacks and original causes. Final candidate
measurements were refreshed after these corrections; the initial record remains historical with its own hashes.

  Rationale: callers need both readable failures and inspectable data without parsing message text.

## Context and Orientation

Public exceptions live in src/main/java/com/taitl/existential/exceptions/. At baseline ExistentialException provided
only
standard message/cause constructors. ExistentialExceptions stores sibling exceptions in multiple(), uses the first as
its cause, and attaches the remainder as suppressed. Preserve that compatibility even though structured siblings are
not a semantic cause chain. ValidationReport in com.taitl.ex.logic.stages.validation.output collects failures;
ValidateTransaction throws ValidationStageExceptions after evaluation.

At handoff, HEAD is 28760cb0cb25c3cdccaec3ec128395891b969e60 and the working tree also contains preceding Sprint 09
access-event/description fixes, acceptance tests, and performance records that are not committed. This is orientation,
not an instruction to reset. Inspect status and preserve all tracked/untracked work before preparing the baseline.

InvariantBuilder, IntentBuilder, and EffectBuilder delegate declaration to rule sets. On and Expression implementations
hold descriptions. IndexEvs, ConfigurationIndexes, and OrderlyEv prepare ordered rules; the compiled RuleInventory and
EventField paths cache selection. Transaction-local StageData overlays belong to the active handle. A rule occurrence
means one declaration at one origin, even if another origin reuses the same callback object.

ExecuteHandler and ExecuteHandlers invoke checks/effects; EvaluateIntent and EvaluateSplitKeys authorize reported
events. A selected rule can be general or derived from an event family, so its event/type may differ from the original
report. The diagnostic must distinguish declaration facts from invocation facts. Boundary means the call triggering
evaluation, such as checkpoint or commit; it is separate from the configured stage.

## Interfaces and Dependencies

### Public diagnostic surface

Add the read-only interface com.taitl.existential.diagnostics.Diagnostic, extending java.io.Serializable.
Library-created implementations are immutable snapshots with these no-argument accessors:

    DiagnosticCode code();
    String message();
    String operation();
    String rule();
    String context();
    boolean transactionLocal();
    String event();
    String type();
    String ruleEvent();
    String ruleType();
    StageName stage();
    String boundary();
    boolean evaluationStopped();
    List<String> notes();
    List<String> actions();
    String troubleshooting();
    List<Diagnostic> children();

code and message are mandatory; other scalar values are nullable when unknown/absent. Lists are non-null immutable
copies and preserve order/duplicates. rule is the existing description, never a separate identifier. Empty/absent
optional descriptions omit the field; preserve supplied nonempty text without trimming. context is the original
declaration path/pattern; transactionLocal distinguishes a local rule with null context from missing provenance.
event/type describe the reported event and TypeKey evidence; ruleEvent/ruleType describe the selected declaration.
Store strings rather than Class, reflective Type, TypeKey, entity, callback, Throwable, or handle references.

stage uses the existing com.taitl.existential.constants.StageName; render it with Locale.ROOT lowercase, not label().
boundary is one of report, begin, checkpoint, commit, rollback when known. A begin-stage entity rule triggered by
reporting has stage BEGIN and boundary report; a transaction begin callback has boundary begin. evaluationStopped
means this evaluation is known to have stopped because of failure; false is not an exhaustive-validation guarantee.
Aggregate children represent sibling failures in existing order, not their causal relationships. A child diagnostic
retains its complete fields even when the aggregate renderer suppresses repeated transaction information.

Add ExistentialException.diagnostic(), returning Diagnostic or null for an undecorated failure. No Optional, public
metadata builder, rule-ID setter, or rule declaration overload is needed. Caller-created exceptions using existing
constructors keep their old message/cause behavior until emitted through the selected runtime evaluation paths.
New metadata-bearing constructors append a Diagnostic as a third argument to existing message/cause forms; do not
add a one-argument Diagnostic overload that makes existing null calls ambiguous. Cover the selected stock exception
types. For aggregates, use named diagnosed factories instead of competing varargs constructor overloads:

    ExistentialExceptions.diagnosed(String stage, Diagnostic diagnostic, ExistentialException... multiple)
    ValidationStageExceptions.diagnosed(Diagnostic diagnostic, ExistentialException... multiple)

Use protected metadata-bearing constructors to implement those factories. Preserve existing aggregate stage(),
multiple(), first-cause, suppressed members, and defensive array copying. Diagnostic data carries no Throwable;
causes remain on the exceptions. Do not mutate a callback-supplied exception to attach invocation-specific metadata.
Never reuse an invocation diagnostic across separate throws/transactions.

### Initial code catalog and exception compatibility

Add com.taitl.existential.diagnostics.DiagnosticCode with id() returning the stable display string below. Each entry
has a stable troubleshooting path under /Troubleshooting.md#diagnostic-<lowercase-display-id>. Add those headings
when implementing; do not publish dead links in emitted failures. Enum constants use underscores, display IDs hyphens.

RULE_REJECTED displays RULE-REJECTED: an ordinary failed check/expression, retaining the existing stock
ConditionNotMetException, InvariantViolation, or PredicateFailure classification. The primary message is Rule rejected;
the description appears once in the rule field. Legacy cause-free condition EventHandlerException behavior remains
collectable as before, with classification decided before rendering.

INTENT_REJECTED displays INTENT-REJECTED: a matching intent rejected the event. Throw IntentViolation with the actual
failed declaration/description and original rejection details; do not collect it as an ordinary validation violation.
INTENT_MISSING displays INTENT-MISSING: a guarded event has no matching intent. Throw IntentViolation without an
invented rule/context, with the useful action Define a matching intent for this event/type or review intent gating.

CALLBACK_FAILED displays CALLBACK-FAILED: an unexpected RuntimeException from a rule or lifecycle callback. Existing
EventHandlerException and intent-callback IntentViolation remain their existing outer stock types. A raw unexpected
RuntimeException from a non-intent callback is wrapped in EventHandlerException so diagnostic() is available; retain
the original exception as cause. An unexpected intent callback failure uses IntentViolation with this code. These
failures remain immediate and cannot become ordinary collected violations. Preserve Error propagation unchanged.

EVALUATION_FAILED displays EVALUATION-FAILED: the aggregate boundary failure, retaining ValidationStageExceptions
or the existing stage aggregate type. Its primary message states the stage and collected failure count. Its children
match multiple() exactly in number/order. Add the failed boundary's rollback-only consequence once after the handle
state transition, without copying that note into every child.

Copy stock library-origin failures without losing their underlying causes, stack traces, or suppressed failures.
If a callback supplies its own exception/custom subclass, retain that object as cause under the corresponding stock
outer exception instead of mutating it or reflectively guessing constructors. Thus stock library catches remain
supported; the exact runtime class of an arbitrary callback exception is available through its cause. The raw-callback
wrapping policy is an intentional compatibility change and must be stated in usage/troubleshooting notes and tests.

### Rendering and internal ownership

Use DiagnosticLogic under com.taitl.ex.logic.diagnostics with BuildDiagnostic, DiagnoseFailure, RenderDiagnostic, and
EscapeDiagnosticText actions and a separate immutable snapshot data unit. Keep fields/delegates grouped with @Logic;
use Creator for delegates and keep models free of business logic. Pass provenance and boundary data explicitly;
do not introduce thread-local ambient state, an entity registry, or retained live evaluation objects.

Default getMessage() renders plain text lazily and memoizes the result safely on that exception. Rendering reads only
snapshot data, never calls entity/Throwable toString or callback-supplied formatters, and does not scan stack traces.
Keep the original fallback message. If formatting fails with a RuntimeException, return that fallback rather than
masking the original failure; no recursive rendering/relogging. Diagnostic creation failures likewise leave the
original failure propagating, without retries or user callback invocation. Do not catch VM Errors for decoration.

The primary line is error[CODE]: <message>. Emit nonempty fields in operation, rule, context, event, evaluation order.
Render event/type together and stage/boundary together. For a local rule use context: transaction-local, while raw
context remains null and transactionLocal is true. Additional differing rule event/type labels follow evaluation.
Then render notes, actions, and the troubleshooting path. Escape embedded CR/LF/tab/control characters in field text
without changing raw values. Do not truncate caller descriptions silently. Missing optional fields leave no placeholder.

Aggregate output has one primary/count line, common operation/evaluation and transaction notes once, and indented
child diagnostics in existing order. Suppress a child's operation/evaluation only when equal to the enclosing values;
retain its rule/context/event and any differing evaluation. Do not also render cause/suppressed trees as sibling
diagnostics; standard printStackTrace remains responsible for Throwable causality. getMessage returns the detailed
rendering, while Diagnostic.message returns the concise category/summary for programmatic use.

No JSON wire format, source-file capture, ANSI colors, configurable rendering policy, or external dependency is added.
General definition reuse, mutation-after-begin, supplied-rule binding, snapshot policy, global caches/shutdown errors,
custom event APIs, and all-public-exception coverage remain outside this selected implementation contract.
