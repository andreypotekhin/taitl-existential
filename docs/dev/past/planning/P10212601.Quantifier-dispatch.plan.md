# Restore fluent entity quantifier dispatch


## Purpose


Fluent invariant all/exists rules must reject invalid reported entities during checkpoint/commit validation.
T10212601 established that their dispatch keys never reach runtime lookup. This plan delivers that correction,
replaces the cat workflow workaround, and verifies previously dormant example configurations.

## Decision Log


Bare expressions apply to every reported entity/access event admitted by the existing event API, including deletion.
Validation evaluates ordinary event values, transition after-values, and deletion before-values. Rules run once per
unique encountered event per validation attempt, with existing event deduplication and context/type matching.
Checkpoint repeats validation of retained events; expressions do not imply a global collection scan.
Event-specific predicates remain scoped to their event. Application collections/indexes remain caller-owned.

Register expressions under Expression plus their declared TypeKey, and include that key once for each distinct matched
runtime TypeKey. This is an internal lookup route, not a new business event. Merge with event handlers using the existing
global declaration ordering and EventField cache. No new registry, entity retention, or public API is needed.

## Context and implementation


IndexEvs currently indexes bare expressions by their concrete Java class. SplitEvent builds a MultiKey only from
runtime business events; ExecuteHandlers already supports expression evaluation and selects the endpoint above.
Change IndexEvs.eventKey and SplitEvent.multiKey. Preserve full/simple names consistently, generic type expansion,
event ordering, intent lookup, and transaction-local expression registration.

Add specification acceptance under src/test/java/com/taitl/specs/library_usage. Cover fluent missing-key rejection,
positive collection/map matches, false All, conditional All, event scope, explicit transition/deletion endpoints,
checkpoint and commit, rollback after rejection, duplicate splits, cached lookup across transactions, type isolation,
and full/simple names. Add a negative relocation-dwelling case and verify location validation in the example.
Use the existing configured class rules, not mocked event fields, so registration-to-commit is exercised.

## Remaining topic decisions


Broader index naming, relationship multiplicity, index mutation/concurrency and transactional index maintenance,
and quantification over transition objects remain outside this defect. Their specification claims are not marked
verified by this correction. Keep these implementation/readiness decisions in project/planning records.

## Recovery and resource hygiene


Dispatch failure follows existing validation recovery: failed commit detaches the transaction; explicit rollback
releases its data. Checkpoint failure retains its existing recovery behavior. Application objects and relationship
indexes are not undone. Cached lookup keys contain type/event metadata, not runtime entity values; the existing
configuration owner controls their lifetime. Do not expand caching to entity values or add transaction-global state.

## Surprises & Discoveries


Initial investigation: fluent Exists/All predicates are never called for create; direct Exists and event-bound
Exists reject correctly. Runtime endpoint extraction already matches the selected contract.

The initial acceptance run executed 25 tests: 23 failed and one transaction-overlay path errored because skipped
expressions left an empty lookup. Shared dispatch corrected those paths. Two remaining generic failures exposed
reflection's comma-space separator versus runtime expansion's comma separator; canonicalizing reflected type names
fixed both expression and handler matching without changing generic erasure policy. Final acceptance has 26 cases,
plus six cat-workflow tests. The 32 focused cases pass. Existing example configurations required no rule changes.
