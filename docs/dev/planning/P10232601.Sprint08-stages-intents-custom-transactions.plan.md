## Purpose / Big Picture

After this change, successful checkpoints continue to accept events, failed checkpoints leave a rollback-only handle that can still be explicitly cleaned up, all applicable authorization intents must pass, and validation preserves ordered effects while collecting failures safely. Applications can keep using per-transaction rule configuration with runtime values; disposal must release transaction-local callbacks. The observable proof is the specification test suite and `mvn clean install` from the repository root.

## Surprises & Discoveries

- Observation: checkpoint lifecycle currently disables both begin and immediate report processing before checkpoint evaluation.
  Evidence: `ConcreteTr.onCheckpoint()` sets `beginActive` and `immediateActive` to false.
- Observation: report selections currently retain handler order but not whether a handler came from an `Effect` declaration.
  Evidence: `OrderlyEv`, `RuleDeclaration`, and `RuleSelection` currently carry only callback/order/selection data. This metadata is needed to distinguish an effect that participates in the current event from an unrelated effect at another stage or event.

## Decision Log

- Decision: keep the existing exception-based checkpoint/commit failure API; collect violations in `ValidationReport` and throw the current aggregate stage exception after evaluation.
  Rationale: this matches the selected Sprint 08 contract and avoids a new reporting API.
  Date/Author: 2026-10-23 / user and implementation agent.
- Decision: stop a validation traversal after the first ordinary violation only when an effect handler was selected for that evaluation. Checks-only traversals continue collecting. Handler order stays the configured declaration order.
  Rationale: this preserves successful side-effect order and avoids running later effects after a failed precondition.
  Date/Author: 2026-10-23 / user and implementation agent.
- Decision: checkpoint failure applies the same rollback-only state and active-registry detachment as commit failure; explicit rollback and close remain valid, and rollback callbacks remain explicit-only.
  Rationale: the handle cannot safely continue after a failed boundary evaluation, while cleanup remains under caller control.
  Date/Author: 2026-10-23 / user and implementation agent.
- Decision: keep mutation-after-begin, transaction-definition reuse, and snapshot semantics outside this implementation contract until separately decided.
  Rationale: the runtime custom-rule use case does not settle those broader semantics.
  Date/Author: 2026-10-23 / user and implementation agent.

## Context and Orientation

The authoritative behavior is in `docs/dev/specifications/TransactionsAndEvaluation.spec.md` and `docs/dev/specifications/IntentsAndEffects.spec.md`; rationale is in their paired design documents. `ConcreteTr` owns the public transaction handle state. `TransactionLogic` owns the ID registry and dispatches checkpoint/commit/rollback actions. `EvaluationLogic` walks reported event keys and coordinates authorization and configured handlers. `ConfigurationIndexes`, `ConfiguredHandlers`, `OrderlyEv`, `RuleInventory`, and `RuleSelection` preserve declaration order and provide cached handler selections. Transaction-local rules are indexed into per-handle `StageData` overlays and disposed by `ConcreteTr.close()`.

An ordinary violation is a known failed invariant/condition that enters `ValidationReport`; an unexpected callback failure or authorization denial throws immediately. An effect is a handler declared through `Effect<T>`. A selected effect participates when it appears in the event's current ordered handler selection; an effect configured for a different stage or unmatched event does not participate.

## Validation and Acceptance

Acceptance follows the Sprint 08 section in `docs/dev/project/sprints/Sprint08_V2StagesIntentsAndCustomTransactions.md`. A successful checkpoint must permit subsequent events and immediate intent checks while retaining once-per-key begin history. A failed checkpoint must throw, detach ID lookup, reject further work/commit/checkpoint/memo access, and allow explicit rollback or close; callback execution remains explicit. Every matching intent must pass, while an explicit predicate disjunction remains a way to grant alternatives.

Checks-only boundary evaluation must collect violations across multiple entities before throwing the existing aggregate exception. When an effect is selected, successful checks/effects run in declaration order; an ordinary violation is added to the report and stops all later work, including later entities. A violation after an earlier effect leaves that effect performed. Unexpected failures and intent denials stop immediately. Effects in other stages or unmatched handlers do not force the early-stop policy. Custom transaction acceptance must demonstrate runtime values, per-handle isolation, and callback release after disposal.
