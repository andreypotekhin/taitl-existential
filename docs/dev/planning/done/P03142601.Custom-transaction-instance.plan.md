# Implement executable custom transaction instances

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

This plan is maintained according to `/docs/dev/auto/Plans.md`.

## Purpose / Big Picture

Users should be able to build a request-scoped `Transaction` object, attach rules that capture dynamic data such as
method arguments or HTTP request parameters, pass that object to `Ex.begin(op, custom)`, and have those rules execute
as part of the existential transaction. After this change, a user can prove the feature by creating a custom
transaction subclass with a field like `requiredColor`, attaching an invariant or effect that reads that field, and
observing that the rule fires during event processing and commit.

Today the public API already exposes `Ex.begin(op, custom)` and the runtime already executes lifecycle handlers and
indexes intents from runtime `Transaction` objects, but validation-stage rules from those transaction instances are not
prepared for evaluation. The result is that the API surface exists while the user-visible behavior promised by the
specification is still incomplete. Because transaction configuration happens on the business-transaction path in this
repository, the implementation must keep per-event costs minimal and should prefer reusing and refactoring existing
indexing components over adding a second evaluation pipeline.

## Surprises & Discoveries

- Observation: the current specification test for `Custom transaction instance` only proves that `ex.begin(op, custom)`
  does not throw when given an otherwise empty `Transaction`.
  Evidence:
  `/src/test/java/com/taitl/existential/specs/configuration_workflow/custom_transactions/`
  `UserCanConfigureCustomTransactions.java`
  creates `new Transaction(op, "request-scope")`, emits an update, and asserts only that no exception occurs.

- Observation: lifecycle handlers and intents from runtime `Transaction` objects already participate in execution, but
  invariants and effects do not.
  Evidence: `/src/main/java/com/taitl/ex/logic/tr/actions/ExecuteLifecycle.java` iterates over `tr.transactions()`,
  and `/src/main/java/com/taitl/ex/logic/tr/actions/IndexIntents.java` indexes runtime transaction intents, while
  `/src/main/java/com/taitl/ex/logic/stages/validation/actions/PrepareTransaction.java` is empty and
  `/src/main/java/com/taitl/ex/logic/evaluation/EvaluationLogic.java` resolves handler indexes only from
  `config(tr).indexes(...)`.

- Observation: the runtime already establishes a deterministic placement for the caller-supplied custom transaction:
  it is appended after all matched context transactions.
  Evidence: `/src/main/java/com/taitl/ex/logic/transactions/actions/CreateTran.java` adds matched context transactions
  first and then calls `o.addTransaction(custom)` when a custom instance is provided.

- Observation: this repository explicitly treats transaction configuration as a performance-critical path, not a
  startup-only concern.
  Evidence: `/docs/dev/Development.md` says the library emphasizes performance for parts that run as part of a
  business transaction, including "Configuring the rules for a transaction".

- Observation: the current builder path already constructs and populates transaction rule containers on each begin.
  Evidence: `/src/main/java/com/taitl/existential/builders/TransactionBuilder.java` installs a context transaction
  factory that creates a `Transaction` instance and replays configured `Evs<?>` suppliers into it at runtime.

## Decision Log

- Decision: API compatibility is not a constraint for this work; refactor public or internal transaction APIs if that
  yields a simpler or faster transaction model.
  Rationale: the library has not been released yet, so preserving current shapes is less important than ending with a
  cleaner high-performance design. `Ex.begin(op, custom)` remains the default external shape only if it survives that
  scrutiny.
  Date/Author: 2026-03-14 / Codex Planner

- Decision: prefer the simplest model that preserves context matching, inheritance, and request-scoped customization;
  the initial implementation target remains additive composition because it reuses the existing runtime assembly order.
  Rationale: additive composition lets the feature land by extending current machinery rather than inventing a
  parallel transaction-selection model. If implementation reveals that substitution is materially simpler and faster,
  revise this plan before coding that deeper refactor.
  Date/Author: 2026-03-14 / Codex Planner

- Decision: optimize the event-time path over the begin-time path.
  Rationale: some begin-time preparation is intrinsic for request-scoped transaction rules, but repeated list merging,
  handler scans, or cache misses on every event would penalize the core validation loop for the entire transaction.
  Date/Author: 2026-03-14 / Codex Planner

- Decision: prepare transaction-scoped handler overlays once per `Tr` and expose them through the same lookup surface
  used by static configuration indexes, rather than adding a second evaluation pipeline or mutating shared caches.
  Rationale: this maximizes reuse of the current indexing and split-event machinery while keeping prepared state
  transaction-local and avoiding repeated per-event composition work.
  Date/Author: 2026-03-14 / Codex Planner

- Decision: preserve execution order as `context rules first, transaction rules second`, with transaction rules ordered
  by `tr.transactions()` and therefore placing the caller-supplied custom transaction last.
  Rationale: this is consistent with the current runtime assembly order and with the existing suggestion to treat the
  custom transaction instance as the final, most-specific contributor.
  Date/Author: 2026-03-14 / Codex Planner

## Context and Orientation

This repository uses two different transaction concepts that matter for this plan. A `Tr` in
`/src/main/java/com/taitl/existential/transactions/Tr.java` is the live existential transaction for one business
operation such as `"/api/cats/update"`. A `Transaction` in
`/src/main/java/com/taitl/existential/configs/Transaction.java` is a rule container attached to that `Tr`. Multiple
`Transaction` instances can participate in a single `Tr`: one from each matching context transaction factory, plus an
optional caller-supplied custom transaction instance passed to `Ex.begin(op, custom)`.

The `Ex.begin(op, custom)` call flows through `/src/main/java/com/taitl/existential/Ex.java`,
`/src/main/java/com/taitl/existential/Existential.java`,
`/src/main/java/com/taitl/ex/core/existential/ExistentialTransactions.java`, and
`/src/main/java/com/taitl/ex/logic/transactions/TransactionLogic.java`. The `TrRegistry` delegates creation to
`/src/main/java/com/taitl/ex/logic/transactions/actions/CreateTran.java`, which creates a `Tr`, adds context-derived
`Transaction` objects in matching order, and finally appends the caller-supplied custom transaction if one exists.

The runtime already supports part of transaction-scoped behavior. Transaction lifecycle handlers (`begin`, `commit`,
`rollback`, `checkpoint`) execute because `/src/main/java/com/taitl/ex/logic/tr/actions/ExecuteLifecycle.java`
iterates over `tr.transactions()`. Transaction intents work because
`/src/main/java/com/taitl/ex/logic/tr/actions/IndexIntents.java` indexes them into `ConcreteTr` stage data when a
transaction is added.

The missing piece is event-based rule evaluation for transaction-scoped invariants and effects. Context-scoped rules
are preindexed into `/src/main/java/com/taitl/ex/logic/configuration/indexes/ConfigurationIndexes.java` through
`/src/main/java/com/taitl/ex/logic/configuration/indexes/actions/IndexConfig.java`. Event evaluation in
`/src/main/java/com/taitl/ex/logic/evaluation/EvaluationLogic.java` reads those context indexes through `eventField`.
No corresponding preparation exists for runtime `Transaction` objects: `PrepareTransaction.call(...)` is empty, so
transaction-scoped invariants and effects never reach event evaluation.

For this plan, "custom transaction instance" means a caller-created `Transaction` or subclass instance passed to
`Ex.begin(op, custom)`. "Prepared runtime indexes" means per-`Tr`, per-stage handler lookup structures built from the
`stage()` contents of the participating `Transaction` objects. "Prepared overlay" means a transaction-local lookup
object that reuses static configuration indexes and overlays only the additional transaction-scoped handlers needed for
this `Tr`. The zero-extra-cost fast path means that when no runtime invariant or effect rules are present, event
evaluation continues to hit the shared static indexes directly.

## Plan of Work

Milestone 1 introduces a characterization spec that proves the missing behavior and locks the desired semantics.

Update
`/src/test/java/com/taitl/existential/specs/configuration_workflow/custom_transactions/`
`UserCanConfigureCustomTransactions.java`
so the `Custom transaction instance` scenario uses a concrete custom `Transaction` subclass with a request-scoped
field. Attach at least one transaction-scoped validation rule directly to that instance before calling `ex.begin(op,
custom)`. The strongest proof is a rule that reads request-scoped state and affects commit behavior, for example a
custom invariant on `Cat` updates that compares the updated entity against a field like `requiredColor`, plus a custom
effect that records the request-scoped value into an `AtomicReference`. The current code should fail this stronger
test because the invariant or effect is never indexed for evaluation. Keep the existing lifecycle-focused tests so the
feature continues to cover both old and new behavior.

Milestone 2 adds runtime indexing for transaction-scoped invariants and effects.

Implement the currently empty `/src/main/java/com/taitl/ex/logic/stages/validation/actions/PrepareTransaction.java`
so it builds per-stage handler indexes from `tr.transactions()` as soon as a transaction begins. The clean design is
to prepare dedicated runtime overlays once, store them on the live `Tr` or `ConcreteTr`, and reuse them across begin,
immediate, commit, checkpoint, and validation evaluation. Do not rebuild indexes on every event.

Reuse the existing event-key derivation logic instead of duplicating it. The most maintainable path is to extract the
rule-walking logic from `IndexConfig` into a focused helper that can index any ordered stream of `Evs<?>` collections
into a `ConfigurationIndexes` instance. That helper should allow `PrepareTransaction` to index transaction-scoped
`Invariant` and `Effect` rule sets while ignoring `Intent` and `Life`, because those two categories already have
separate runtime paths.

The prepared structure should be sparse. If no participating runtime transaction contributes `Invariant` or `Effect`
rules for a stage, do not allocate an overlay for that stage and let evaluation continue through the shared static
`ConfigurationIndexes` objects.

Milestone 3 composes context and transaction indexes during event evaluation.

Extend the runtime so `EvaluationLogic.eventField(tr, stageName)` can see both sources of rules: the existing static
context indexes for the operation and the prepared transaction overlay for that `Tr`. Introduce a small overlay lookup
type, for example under `/src/main/java/com/taitl/ex/logic/configuration/indexes/data/`, that presents the same
surface as `EventField` while caching merged `MultiKey` lookups once per transaction. Its `get(MultiKey)` method must
return context handlers first and prepared transaction handlers second. Its `hasBiEventKey(EventKey)` method must
report true if either source contains the key, because `RequireMemoForBiEvents` relies on that check to decide whether
split bi-events need memo state.

The prepared transaction indexes must follow `tr.transactions()` order. That preserves parent-context transaction
rules before child-context transaction rules and places the caller-supplied custom transaction last. Within a single
transaction, preserve the order in which rules were added to the transaction’s `Stage`.

Do not add repeated per-event concatenation work on the hot path. The overlay should cache merged handler lists by
`MultiKey`, just as the current `EventField` caches handler resolution for static indexes.

Milestone 4 adds regression coverage and completes the documentation trail.

Add focused tests around the new runtime preparation layer. At minimum, cover one spec that proves a custom
transaction instance contributes a validation rule, one regression that confirms lifecycle handlers still execute for
custom transaction types, and one regression that confirms bi-event memo enforcement still notices transaction-scoped
`Transit` or `Port` handlers through the overlay event field. Update `/docs/dev/Specification.md` by prefixing the
`Custom transaction instance` story with `+` only after the new spec passes. If the implementation introduces a new
failure mode or error message while preparing runtime indexes, document the remedy in `/Troubleshooting.md` and link to
it from the exception message.

`mvn -q test` passes from the repository root.

If the implementation touches memo-sensitive bi-event evaluation, a regression test proves that missing memo state is
still detected when the relevant bi-event handler is configured on a runtime transaction rather than only in a static
context.

The final code path for transactions without runtime invariants or effects does not add a new repeated per-event
handler merge or scan; the fast path remains the shared static index lookup.

## Idempotence and Recovery

The implementation is additive and safe to repeat. Prepared overlays must be transaction-local and cleared with the
lifetime of the `Tr`; they must never leak into shared configuration caches. If a step goes wrong, revert the changes
to the runtime overlay preparation and event-field overlay, rerun `mvn -q test`, and confirm the repository is back to
the planning-time baseline.

No new external dependencies are needed. Reuse the existing configuration-indexing infrastructure, memo-resolution
checks, and transaction stage model.
