# Implement execution stages for rule storage and evaluation

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and
`Outcomes & Retrospective` must be kept up to date as work proceeds.

See `/docs/dev/auto/Plans.md` for the ExecPlan contract and keep this document aligned with those requirements.

## Purpose / Big Picture

Users can already configure invariants, effects, intents, and transaction lifecycle handlers, but the runtime currently
stores these rules as a flat list and does not model explicit execution stages. After this change, rule declarations are
partitioned into explicit stages (`Precondition`, `Immediate`, `Validation`) with deterministic defaults, users can set
the target stage via configuration APIs/builders, and runtime evaluation executes stage-appropriate rules at stage-
appropriate times (transaction start/runtime/commit-checkpoint). This is observable through tests proving that
precondition handlers execute once per trigger event key, immediate handlers execute on every trigger event, and
validation handlers execute on commit/checkpoint.

## Surprises & Discoveries

- Observation: `FinalizeConfiguration.call()` currently throws "You need to configure at least one context" whenever
  only builder-backed contexts exist, because it checks the built-config registry before build finalization.
  Evidence: Running `mvn -q -Dtest=UserCanConfigureCustomTransactions test` fails all tests with that error before stage
  logic is reached.

- Observation: Config indexing was invoked before config registration, causing `Config not found for op ...` during
  finalize.
  Evidence: Stack trace showed `ConfigBuilder.build -> onFinishConfiguration -> indexConfig -> ConfigRegistry.get`
  before `BuildConfigs` called `addConfig`.

- Observation: `ValidationLogic` captured `TransactionLogic.evaluationLogic` before that dependency was initialized.
  Evidence: runtime NPE: `Cannot invoke EvaluationLogic.evaluate(...) because "el" is null`.

- Observation: `ReceiveEvent` captured `ExistentialEvents.indexingLogic` before it was initialized.
  Evidence: runtime NPE from `ReceiveEvent` when indexing read/write events.

- Observation: sibling context chaining could skip finalizing the current context builder.
  Evidence: in `UserCanConfigureCustomTransactions.childContextOverridesInheritedFactory`, root context transaction rules
  were missing until `ContextBuilder.context(...)` auto-finalized pending context work.

## Decision Log

- Decision: Keep intent authorization flow (`EvaluateIntents`) as a dedicated path while still assigning intents to the
  `Immediate` stage for explicit stage bookkeeping.
  Rationale: Intent checks enforce allow/deny semantics and error wording that differ from generic stage evaluation.
  Date/Author: 2026-03-02 / Codex Planner

- Decision: Keep validation-stage evaluation report semantics unchanged and enforce precondition/immediate failures by
  converting non-empty stage reports into `ExistentialExceptions` immediately.
  Rationale: This preserves existing validation aggregation while making runtime-stage failures fail-fast.
  Date/Author: 2026-03-02 / Codex Planner

- Decision: Execute lifecycle handlers from `Tr` lifecycle callbacks across staged `Life` declarations.
  Rationale: lifecycle rules are stage-assigned now and must run on begin/commit/checkpoint/rollback consistently.
  Date/Author: 2026-03-02 / Codex Planner

- Decision: Add nearest-parent config fallback for transaction begin.
  Rationale: operations like `/api/cats/create` must resolve parent-configured contexts/rules when no exact config key
  exists.
  Date/Author: 2026-03-02 / Codex Planner

## Outcomes & Retrospective

Implemented execution-stage modeling and execution end-to-end.

What is now in place:

- Rules are stored in explicit stage buckets through `Stage`/`StageName`.
- Defaults are enforced (`Invariant`/`Effect` -> validation, `Intent` -> immediate, `Life` -> precondition).
- Explicit stage selectors are available in object APIs and builders.
- Configuration indexing is stage-aware for non-intent rules.
- Runtime receives events with precondition-once and immediate-per-event execution.
- Validation evaluates only validation-stage rules.
- Lifecycle handlers execute on transaction lifecycle callbacks.

Additional stabilization done during implementation:

- Finalization and config indexing order was corrected.
- `EvaluationLogic` and `IndexingLogic` initialization-order NPEs were fixed.
- Sibling context chaining now auto-finalizes pending context builder state.

The full Maven suite passes after these changes.

## Context and Orientation

Current rule storage lives in:

- `/src/main/java/com/taitl/existential/configs/Context.java`
- `/src/main/java/com/taitl/existential/configs/Transaction.java`

Both classes store all configured rules in a single `List<Evs<?>>`, despite `/docs/dev/Specification.md` defining three
execution stages. Builder wiring lives in:

- `/src/main/java/com/taitl/existential/builders/ContextBuilder.java`
- `/src/main/java/com/taitl/existential/builders/TransactionBuilder.java`

Configuration indexing and lookup lives in:

- `/src/main/java/com/taitl/ex/logic/configuration/indexes/ConfigurationIndexes.java`
- `/src/main/java/com/taitl/ex/logic/configuration/indexes/actions/IndexConfig.java`
- `/src/main/java/com/taitl/ex/logic/configuration/indexes/data/EventField.java`

Runtime evaluation entry points are:

- Event-time path: `/src/main/java/com/taitl/ex/logic/events/actions/ReceiveEvent.java`
- Validation-time path: `/src/main/java/com/taitl/ex/logic/evaluation/EvaluationLogic.java`

Transactions are represented by `/src/main/java/com/taitl/existential/transactions/Tr.java` and transaction lifecycle
entry points are in `/src/main/java/com/taitl/ex/logic/transactions/actions/`.

## Plan of Work

Introduce stage primitives in the public config package (`StageName`, `Stage`) and use them as the source of truth for
where each `Evs<?>` rule collection belongs. Keep existing public methods (`invariant`, `effect`, `intent`, `cycle`) as
default-stage conveniences while adding explicit stage selectors (`precondition`, `immediate`, `validation`) in both
object APIs and builders.

Update builder internals so each deferred rule supplier captures its target stage at definition time. Update context and
transaction build routines so they add each rule to the correct stage bucket instead of a single flat list.

Update configuration indexing so non-intent rules are indexed per stage and are retrievable via stage-specific
`EventField` views. Keep intent indexing dedicated because authorization semantics are specialized.

Update runtime flow:

- On event receive, evaluate immediate rules every time.
- On event receive, evaluate precondition rules once per event key during a transaction.
- On commit/checkpoint, evaluate only validation-stage rules.
- On transaction start, activate runtime-stage processing.

Add targeted tests for stage routing and execution behavior and keep existing behavior-compatible tests green.

- Validation-stage rules execute on commit/checkpoint through existing validation path.
