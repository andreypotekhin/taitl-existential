# Implement SplitEventType event expansion per Javadoc

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and

This plan is maintained according to `/docs/dev/auto/Plans.md`.

## Purpose / Big Picture

`SplitEventType` currently covers only a narrow subset of event families (`Port`, `ReadAndLock`) and rejects
`Transit`. As a result, configured rules on combined event types (`CU`, `UD`, `CUD`) or cross-family matches from
elementary events (`Create`, `Update`, `Delete`) can be skipped during lookup. After this change, event splitting will
follow the class Javadoc contract in a deterministic and bounded way, event classes will define collection-friendly
`equals/hashCode`, and a behavioral flag will allow disabling elementary-to-compound expansion when users do not want
synthetic bi-state semantics (`t0 == t1`) for single-entity roots.

A user can observe the change by splitting each event family in tests and seeing the expected emitted event types
present in the split key set.

## Surprises & Discoveries

- Observation: `SplitEventType.call(...)` currently rejects `Transit` and leaves most event families unimplemented.
  Evidence: `/src/main/java/com/taitl/ex/logic/evaluation/events/split_events/event_splitter/SplitEventType.java`
  has `check(!(event instanceof Transit<?>), "Please specify event of type Port<>");` and `// TODO` markers.

- Observation: The Javadoc requires bidirectional family mapping, but a naive recursive closure can form cycles.
  Evidence: Mappings include `Port -> Create` and `Create -> Port`; similarly `Transit -> Update` and
  `Update -> Transit`.

- Observation: `Event` subclasses do not override `equals/hashCode`, so `Set<Event<T>>` deduplicates by object
  identity, not semantic event meaning.
  Evidence: Event classes (`Create`, `Update`, `Delete`, `CU`, `UD`, `CUD`, `Transit`, `Port`) inherit identity-based
  `Object.equals`. Re-emitting logically equivalent events as fresh objects would not dedupe automatically.

- Observation: Split output can include bi-event keys (`Port`, `Transit`) even when the original runtime event is
  single-entity, which can affect handler execution semantics.
  Evidence: `ExecuteHandlers.call(...)` executes handlers against the original runtime event from `SplitResult`, not
  against each split event instance.

- Observation: Intent evaluation currently treats bi-handlers as inapplicable for single-entity runtime events.
  Evidence: `EvaluateIntent.call(...)` returns `false` for `BiEventHandler` when `event` is not `BiEvent`.

- Observation: Intent split path already evaluates handlers against split runtime events (not the original root event),
  so synthetic `(t, t)` adaptation is required in `ExecuteHandlers` but not in `EvaluateIntent`.
  Evidence: `EvaluateIntents.splitAndGroupByEventType(...)` groups the result of `EventSplitter.split(...)`, and
  `EvaluateSplitKeys` passes `primaryRuntimeKey.event()` from each split group to `EvaluateIntent.call(...)`.

## Decision Log

- Decision: Implement Javadoc behavior as a strict two-pass, root-driven expansion, not recursive closure.
  Rationale: Two-pass expansion matches the Javadoc structure, avoids cycle amplification, and keeps runtime cost
  bounded and predictable.
  Date/Author: 2026-03-03 / Codex Planner

- Decision: Add `equals/hashCode` to base event carriers (`EntityEvent`, `BiEvent`) as a prerequisite, using exact
  runtime event class plus entity-reference identity (`==`) for equality semantics.
  Rationale: This enables deterministic deduplication for split events without relying on mutable entity value-based
  equality.
  Date/Author: 2026-03-03 / Codex Planner

- Decision: Introduce a disable flag for elementary-to-compound expansion:
  `Flags.EVENT_SPLIT_DISABLE_ELEMENTARY_TO_COMPOUND` (default: off, meaning expansion enabled).
  Rationale: Some users need strict non-synthetic bi-state semantics and must be able to opt out per runtime.
  Date/Author: 2026-03-03 / Codex Planner

- Decision: When a bi-handler is evaluated for a single-entity root event under enabled expansion, adapt payload as
  `(t, t)` to match the user-approved model that one runtime entity pair applies across split families.
  Rationale: This preserves the ability to resolve bi-family handlers from elementary roots while keeping execution
  deterministic; users who do not want this can disable elementary-to-compound expansion via the new flag.
  Date/Author: 2026-03-03 / Codex Planner

- Decision: If `SplitEventType` exceeds readability limits during implementation, split mapping logic into focused
  delegates in the same package.
  Rationale: Keep class sources lean and maintainable per project style guidance.
  Date/Author: 2026-03-03 / Codex Planner

## Context and Orientation

The split pipeline starts in `/src/main/java/com/taitl/ex/logic/evaluation/events/split_events/SplitEvent.java`,
which calls `EventSplitter.split(...)`. `EventSplitter` delegates event-family expansion to
`/src/main/java/com/taitl/ex/logic/evaluation/events/split_events/event_splitter/SplitEventType.java`.

`EventSplitter.split(...)` combines split events with split type keys (`SplitTypeKey`) to produce `RuntimeKey` values.
Those keys are combined into a `MultiKey` for `EventField.get(...)`, which resolves configured handlers.

Confirmed model for this task: each runtime evaluation starts from one runtime event payload (single entity or
entity-pair), and that same payload semantics applies across all split event families. Event-type splitting and
type-key splitting remain independent and are recombined into runtime keys afterward.

Tests currently cover only a narrow subset of split behavior:

- `/src/test/java/com/taitl/ex/logic/evaluation/events/split_events/event_splitter/EventSplitterTest.java`
- `/src/test/java/com/taitl/ex/logic/evaluation/events/split_events/event_splitter/SplitEventTypeTest.java`

Current implementation gaps:

- `SplitEventType.call(...)` supports `Port` and `ReadAndLock` only.
- `Transit`, combined events (`CU`, `UD`, `CUD`), and elementary-to-compound expansion are missing.

## Plan of Work

Milestone 0 introduces prerequisites before split expansion changes:

- Add `equals/hashCode` to `/src/main/java/com/taitl/existential/events/types/EntityEvent.java` and
  `/src/main/java/com/taitl/existential/events/types/BiEvent.java`.
- Add behavior flag `EVENT_SPLIT_DISABLE_ELEMENTARY_TO_COMPOUND` to
  `/src/main/java/com/taitl/existential/constants/Flags.java`.
- Add tests that prove event dedupe works via collection semantics and flag defaults are valid.

Milestone 1 introduces behavioral tests first, so split implementation can be done safely against explicit
expectations.
Add coverage for every mapping family from the Javadoc:

- Compound-style pass (root event expansion):
  `CUD`, `CU`, `UD`, `Transit`, `Port`, `ReadAndLock`.
- Elementary follow-up pass:
  `Create`, `Update`, `Delete` emit matching compound families when absent.

These tests will assert event class presence and key payload identity assumptions needed for downstream key creation.

Milestone 2 implements `SplitEventType` with explicit split functions per root family and bounded two-pass
orchestration with a flag gate on elementary-to-compound pass:

1. Start with incoming event already present in `events`.
2. Pass 1: apply only the root-family expansion rules from Javadoc section 1.
3. Pass 2: if the root event is elementary (`Create`, `Update`, `Delete`) and the disable flag is off, apply Javadoc
   section 2 mappings.
4. Return the same set instance with deterministic insertion order preserved.

Implementation details:

- Add small helper methods to keep class compact and readable:
  `splitCompoundRoot(...)`, `splitElementaryRoot(...)`, `emitIfAbsent(...)`, and family emitters.
- Keep argument validation via `Args.sane`/`Args.check`.
- Preserve existing `ReadAndLock -> Read` and `Port` behavior while extending it.
- Replace the current `Transit` rejection with documented split behavior.
- If the class becomes too large, extract delegates (for example, elementary and compound split maps) in the same
  package and wire them through `SplitEventType`.

Milestone 3 adds regression coverage for complications:

- Recursion guard test: verify each root split terminates with bounded size and does not re-emit endlessly.
- Edge-case tests for null transitions (`Port` create/update/delete branches), `ReadAndLock`, and unsupported custom
  event types (should remain unchanged unless explicitly mapped).
- Runtime compatibility tests around bi-event handler/intent dispatch when split keys include bi-event families for
  non-bi roots. Validate `(t, t)` adaptation behavior and flag-off behavior.
