# Sprint 06: Instance Isolation and Configuration

## Purpose

Make independently constructed `Existential` objects safe to configure and use in the same JVM. An application may
declare rules on one thread, publish the configured instance through normal Java synchronization, and serve concurrent
transactions from other threads. Each instance must retain its own rules, flags, event/transaction state, and shutdown
policy. The static `Ex` facade and `Creator` injection remain explicit process-wide facilities.

## Context and accepted behavior

The authoritative behavior is in [Library and Configuration Specification](../specifications/LibraryAndConfiguration.spec.md),
under Independent library instances, Behavioral flags, and Configuration files. The rationale and tradeoffs are in
[Library and Configuration Design](../design/LibraryAndConfiguration.design.md). Do not add a public configuration
source strategy API in this sprint.

Configure an instance from one thread at a time. Callers coordinate completion of rule declaration and safely publish
the instance; concurrent `begin()` calls are supported and serialize only that instance's first successful
finalization. Flags are prospective and may be changed during setup until finalization succeeds. Checking required
descriptions happens for each newly declared behavior. A failed finalization leaves flags/rules available for repair
and retry. After the first successful `begin()`, flags and rule declarations are fixed. Each configuration source is
validated completely before its values are applied.

## Repository orientation

`Existential` owns the per-instance services. `Ex` delegates to one static instance. `ExistentialInit` loads
`existential.properties` and then the optional file named by `EXISTENTIAL_CONFIG_FILE`. `ExistentialFlags` stores
behavior switches. `ConfigurationLogic`, `ConfigBuilder`, and `FinalizeConfiguration` collect and finalize rules.
`ReceiveEvent`, `EventLogic`, `EvaluationLogic`, and `ExistentialAccess` consume event-related flags. `Creator` and
`CreatorDevice` are global extension points. Specification coverage lives under `src/test/java/com/taitl/specs/`.

## Implementation steps

1. Replace the class-wide configuration-finalization monitor with a per-instance monitor. Safely publish finalized
   configuration state and all built configuration data to threads waiting on concurrent first `begin()` calls.
   Ensure failed construction does not publish the finalized state and still permits retry.
2. Make per-instance flag reads/writes safe for the admitted handoff and transaction concurrency. Reject flag changes
   after successful finalization. Move the required-description check to each newly added invariant/intent behavior so
   a flag update affects subsequent declarations through both old and new builder handles.
3. Remove construction-time snapshots of flags that are meant to apply to subsequent event work. Read event splitting
   and inferred type naming at their documented use points. Keep finalized type-key naming consistent for every rule
   and event index in the instance.
4. Parse each configuration source into validated settings before applying it. Preserve classpath-default then
   environment-selected-file precedence and programmatic override. Keep settings per instance; do not mutate static
   source state.
5. Add direct specification tests for conflicting instances, flag independence/prospective behavior/freezing,
   simultaneous first `begin()`, cross-thread use after a synchronization handoff, independent finalization, and
   invalid-source atomicity/recovery. Keep existing V1 acceptance behavior intact.
6. Reconcile the topic design/specification, traceability, Sprint 06 review, end-user configuration guidance, and
   troubleshooting with observed results. Record setup and first-transaction performance separately from steady
   transaction measurements. Do not claim runtime compatibility beyond tested environments.

## Acceptance and validation

From the repository root, run the required complete build, which selects specification tests through the project's
configured test naming conventions:

    mvn clean install

The acceptance tests must show that two instances with conflicting rules/flags do not affect one another; an instance
configured on one thread can be used after a latch or equivalent handoff; simultaneous initial transactions result in
one successful configuration build; a failed build can be repaired and retried; each flag affects only subsequent
work; post-finalization mutation fails clearly; and malformed configuration values do not partially apply. Inspect
the actual test totals, coverage data/checks, disabled tests, Checkstyle, PMD, Failsafe, and artifact contents.
Measure configuration construction/first begin separately from already-configured transaction workflows.

## Decision log

- Configuration declaration is single-threaded per instance, but ownership is transferable after normal synchronization;
  there is no thread affinity.
- Concurrent first transactions on one instance wait for successful finalization. Different instances do not share a
  finalization lock.
- Flags are prospective; no completed work is revalidated or rebuilt because a flag changes. Required descriptions
  affect each behavior declaration made after the toggle.
- The first successful `begin()` fixes flags and rules. Failed configuration finalization remains retryable.
- Configuration source order is classpath defaults, optional environment-selected file, then programmatic setup.
  Each source is validated before applying its values.
- `Ex` and `Creator` remain explicit JVM-wide facilities. New per-instance injection and configuration-source APIs are
  deferred.
