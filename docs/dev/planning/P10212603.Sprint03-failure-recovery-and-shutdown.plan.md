# Implement V1 Failure Recovery and Graceful Shutdown

This plan delivers the Sprint 03 behavior around caller-owned transaction recovery and deterministic resource release.
It follows `docs/dev/auto/Plans.md`; maintain Progress, Surprises & Discoveries, Decision Log, and Outcomes as work
continues. Behavior belongs to topic specifications; design rationale belongs to topic design documents.

## Purpose / Big Picture

Callers can explicitly recover from failed commits, know which transaction state remains usable after failures, and
close a library instance without racing admitted work. Shutdown can wait indefinitely or for a configured duration.
Rollback attempts all callbacks and releases transaction-owned state even if callbacks fail.

## Decision Log

- Decision: Commit callbacks remain before validation. Rationale: they are part of the commit attempt and may prepare
  state required by validation. Date/Author: 2026-10-21, user.
- Decision: Use immutable `ShutdownPolicy.graceful()` or `ShutdownPolicy.graceful(Duration)`; zero means no timeout.
  Rationale: timeout is a policy value, while only graceful waiting is selected for V1. Date/Author: 2026-10-21,
  user and agent.
- Decision: Support `shutdown.timeoutMillis` in existing properties. Classpath values are overridden by the selected
  environment file, then by programmatic configuration. Date/Author: 2026-10-21, user and agent.
- Decision: Timeout/interruption leaves shutdown draining and retryable; do not force-abort active work. Reject close
  from transaction callbacks. Date/Author: 2026-10-21, user and agent.
- Decision: Failed commits leave no pending registry; explicit rollback callbacks run only when the caller invokes
  rollback. Detached failed handles do not block shutdown. Date/Author: 2026-10-21, user.

## Context and Orientation

`Existential` owns library shutdown and configuration. `TransactionLogic` owns active transaction lookup and lifecycle
calls. `Tr` owns transaction-local runtime indexes, memo data, and prepared stage overlays. The existing properties
loader reads `existential.properties` and optionally the file named by `EXISTENTIAL_CONFIG_FILE`.

## Plan of Work

Add the immutable policy type and expose it through `Existential` and static `Ex`. Parse the nonnegative millisecond
property through the existing configuration loader. In `TransactionLogic`, atomically stop new begins, count in-flight
lifecycle and handler calls, wait for registered active handles, preserve state on timeout or interruption, and
coordinate direct handle close. A completed drain allows `Existential` to close its remaining subsystems.

Keep rollback phase order: transaction lifecycle callbacks first, rollback-stage evaluation second. Continue through
callback failures, retain the first throwable, attach later ones as suppressed, and dispose in `finally`. A failed
begin cleans up its returned handle without running rollback callbacks. A checkpoint failure leaves the handle usable.
Clear prepared indexes, overlay cache, stage handler collections, event caches, memo values, and runtime indexes while
preserving shared configured sources.

Update normative behavior in `TransactionsAndEvaluation.spec.md` and `Housekeeping.spec.md`; record rationale in their
design documents. Keep stage and evidence references here and in sprint/project records.

## Validation and Acceptance

Tests must show that a finite timeout returns while preserving draining state; finishing the registered handle then
allows a retry to close the library. Unlimited wait completes only after explicit transaction completion. New begins
fail after draining starts, while admitted transactions may commit or roll back. Interruption restores the caller's
interrupt status. Close invoked inside an event, intent, or lifecycle callback fails immediately.

Tests must also show that failed begin leaves no registered handle, checkpoint failure permits later work, rollback
attempts callbacks in order despite failures, the first failure remains primary, later failures are suppressed, and
all transaction-owned retained collections clear. The three disabled report tests must execute. Final acceptance
requires `mvn clean install`, verified JaCoCo execution data, zero disabled tests for the covered cases, and separate
failure/cleanup performance evidence. No timing result substitutes for retained-state checks.

## Idempotence and Recovery

Timeout and interruption leave the library draining; finish or directly close registered transactions, then retry
`Existential.close()`. A failed cleanup or validation must not silently clear an active handle. Direct `Tr.close()` is
idempotent, deregisters the active handle, and never invokes rollback callbacks. Caller-owned entity changes and
external callback effects are outside library cleanup.

## Interfaces and Dependencies

`ShutdownPolicy` is an immutable public class with `graceful()`, `graceful(Duration)`, and `timeout()`. `Existential`
and `Ex` expose `shutdownPolicy()` and `shutdownPolicy(ShutdownPolicy)`. The properties key is
`shutdown.timeoutMillis`; it accepts a nonnegative decimal integer, where zero means unlimited wait. No new runtime
dependency is introduced.
