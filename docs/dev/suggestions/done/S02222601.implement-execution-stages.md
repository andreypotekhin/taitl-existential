### S02222601 Implement execution stages

Currently, Context and Transaction store all rules in a single `List<Evs<?>>` while the spec defines explicit stages
(Precondition, Immediate, Validation) and the exceptions already model a stage. This conflates ordering and
execution semantics, makes it unclear which stage a rule targets, and forces runtime logic to infer intent.
Introduce an explicit stage model and partitioned rule storage so evaluation order and stage boundaries are
deterministic and self-documenting.

- Add a `StageName` enum: Precondition, Immediate, Validation.
- Add `Stage` class that owns per-stage `List<Evs<?>>`.
- Update `Context` and `Transaction` to add rules into the correct Stage bucket:
  - Default stage for invariants is Validation
  - Default stage for intents is Immediate
  - Default stage for transaction lifecycle is Precondition
  - Allow to specify exact stage in the API and builders: methods precondition(), immediate(), validation().
- Activate (allow to accept events) Precondition, Immediate stages on transaction start.
- Trigger evaluation of Precondition rules once per trigger event of same type, similarly to how Validation evaluation
is triggered once per event, using a runtime index that ignores duplicate events. 
- Trigger evaluation of Immediate rules each time per trigger event, similarly to how Intent evaluation
  is currently triggered.
- Wire configuration (builder) logic to consume stage-specific instructions.
- Wire evaluation logic to consume stage-specific instructions.
