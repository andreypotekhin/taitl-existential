### S02222601 Stage-partitioned rule storage and evaluation

Context and Transaction store all rules in a single `List<Evs<?>>` while the spec defines explicit stages
(Precondition, Runtime, Validation) and the exceptions already model a stage. This conflates ordering and
execution semantics, makes it unclear which stage a rule targets, and forces runtime logic to infer intent.
Introduce an explicit stage model and partitioned rule storage so evaluation order and stage boundaries are
deterministic and self-documenting.

- Add a `Stage` enum (Precondition, Runtime, Validation) and a `StageRules` container that owns per-stage
  `Instructions` and `List<Evs<?>>`.
- Update `Context` and `Transaction` to add rules into the correct stage bucket, with a clear default stage
  in the API (and a strict opt-in for immediate rules).
- Wire evaluation logic to consume stage-specific instructions so runtime/validation phases no longer scan
  a mixed list.

### S02222601 ContextBuilder should attach configured contexts

ContextBuilder.build() creates a new Context instance and configures it, but never attaches it to the parent
ConfigBuilder. This can silently drop configured rules or transaction factories because ConfigBuilder.build() only
uses its own contexts list. Suggest binding the built context to the parent (either by adding it via
ConfigBuilder.context(Context) or by locating the existing context for the op and applying rule factories to it).

- Decide whether to attach new contexts or mutate existing contexts created by BuildContexts.
- Update ContextBuilder.build() to ensure configured rules end up in the ConfigBuilder contexts list.
- Add a regression test that configured rules are present when a transaction begins.

### S02222601 Key Naming Strategy Injection

Introduce a user-configurable strategy for building TypeKey and EventKey strings, defaulting to the current
simple-name behavior but allowing fully-qualified naming or custom policies. This enables safe extensibility
when multiple libraries define overlapping class names or when custom events share names across packages.

- Add a KeyNamingStrategy interface with defaults for short-name and full-name generation.
- Allow Creator injection for the strategy, and thread it through TypeKey/EventKey factories.
- Document usage in Readme and Specification.md with examples and migration notes.
